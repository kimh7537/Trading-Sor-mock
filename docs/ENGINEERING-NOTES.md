## 1. 이 문서 쓰는 법

### 1.1 답의 틀: 문제 → 원인 → 해결 → 배운 것

질문 하나에 30~60초로 답한다. 순서는 늘 같다.

1. **문제 (5초)** — 무엇이 보였나. 증상 한 문장
2. **원인 (15초)** — 왜 그랬나. 겉원인이 아니라 근본 원인. "테스트가 왜 못 잡았나"까지
3. **해결 (15초)** — 무엇을 했고, **다른 선택지를 왜 버렸나**
4. **배운 것 (10초)** — 다음에 같은 일이 안 생기게 바꾼 규칙 하나

숫자를 하나는 꼭 넣는다(“40건 중 39건”, “1.5M TPS → 376 TPS”, “9/9 잡힘이 가짜”). 숫자가 있으면
직접 한 일로 들린다.

## 3. 가장 중요한 이야기 7개

### 3.1 화면의 "KRX 지정가 매수"가 C에서는 "NXT 시장가 매도"였다 (T6-01)

**상황**
Phase 1~5(71/71)를 닫은 뒤 "각 조각이 아니라 이어서 돌렸을 때"를 보는 감사를 했다. 화면이 보내는 숫자를
C까지 따라갔다.

**증상**
C `types.h`는 `SIDE_BUY=0 · ORDER_LIMIT=0 · MARKET_KRX=0`. 채널계 DTO는 `@Min(1) @Max(2)`, 화면은
`side:1, type:1, market:1`. 중간 변환이 없었다. **화면의 "KRX 지정가 매수"가 C에서는 "NXT 시장가 매도"로
읽혔다.** 그런데 모든 테스트가 통과하고 있었다.

**근본 원인 — 세 겹의 구멍이 겹쳤다**
1. `WireLayoutTest`(T4-02)는 C 헤더를 읽어 **길이만** 대조했다. 배치가 완벽했으므로 통과했다
2. Java 테스트는 1을 넣고 1이 나오는지(왕복)만 봤다. **값의 뜻은 아무도 안 봤다**
3. 원장 데몬 `ledgerd`가 방향·유형·시장을 **읽지도 않고** 성공을 돌려줬다(3.2의 껍데기)

그리고 T5-06 즈음 "WireLayoutTest가 C↔Java 규격 일치를 보장한다"고 보고했는데 틀린 말이었다. 그
테스트의 Javadoc에도 "길이로 잡는다"라고만 적혀 있었다. **테스트가 무엇을 보는지는 이름이 아니라 본문으로
확인해야 했다.**

**어떻게 찾았나**
테스트 결과가 아니라 값의 경로를 사람이 끝까지 따라갔다 — 화면 → REST DTO → 전문 → C 열거형.

**해결**
- Java `WireEnums`, 화면 `lib/wire.ts`를 새로 만들어 날숫자를 전부 **이름**으로 바꿨다
- DTO 검증이 상수를 직접 참조한다: `@Min(SIDE_BUY) @Max(SIDE_SELL)`. 상수와 검증 범위가 따로 놀 수 없다
- `WireLayoutTest`가 `types.h`의 `typedef enum`을 읽어 **값을 양방향으로** 대조한다(자바에만 있는 값,
  C에 새로 생겼는데 자바가 모르는 값). **C의 암묵적 증가(`ORDER_LIMIT = 0, ORDER_MARKET, …`)를 계산한다**
  — 안 하면 첫 항목만 맞고 나머지가 0으로 읽혀 틀린 자바 상수가 오히려 통과한다
- 옛 체계 값(`side:2` 등)은 경계에서 400으로 막히고 원장에 가지 않는다(완료 조건)

**대안과 선택 이유**
- (a) REST는 1부터 두고 채널계가 전문에 실을 때 `-1` → **변환 지점이 하나 더 생기고**, 체결 통보처럼
  거꾸로 올라오는 길에서 `+1`을 또 해야 한다. 한쪽만 빠뜨리면 같은 버그가 거꾸로 난다
- (b) **모든 층이 C의 값을 그대로 쓴다** ← 채택. 전문의 값은 C가 정의하므로 끝까지 그 값을 쓰고, 사람에게
  보여 줄 때만 "매수" 같은 이름으로 바꾼다

**검증 — 버그를 되살려 봤다**
- 변이1 `SIDE_BUY = 1`(옛 체계) → 대조 실패로 잡힘
- 변이2 Java에서 `MARKET_NXT` 삭제 → exit 1이지만 **컴파일 오류**였다. DTO가 그 상수를 참조하므로.
  잡힌 것이 아니다(T5-02 S7/S8과 같은 함정)
- 변이2′ C `types.h`에만 새 값 추가 → "자바가 모른다"로 잡힘
- Java 32/32, 화면 `tsc -b && vite build` 통과

**배운 것**
- 두 언어가 같은 규격을 두 번 적으면 **길이·왕복 테스트는 뜻의 불일치를 못 잡는다**. 값을 한쪽(C)에서 기계로
  읽어 대조해야 한다
- T4-02는 이미 "길이 합이 같고 순서만 다른 배치는 통과한다"는 한계를 적어 뒀다. **적어 둔 한계와 같은 종류의
  구멍이 실제로 터졌다.**

**예상 꼬리 질문**
- Q. 애초에 규격을 한 곳에서 생성(코드 생성)하면 되지 않나?
  A. T4-02 기록에 "순서까지 잡으려면 C가 배치를 기계가 읽을 수 있는 형태로 내보내야 하고, 아직 하지 않았다"고
  적혀 있다. 택한 방법은 C 헤더를 진실로 두고 Java 테스트가 그것을 파싱해 대조하는 것이다. 생성 방식은 하지
  않은 선택지로 말한다.
- Q. 왜 단위 테스트가 다 통과했는데 버그가 있었나?
  A. 각 테스트가 **자기 층의 일관성**만 봤기 때문이다. Java는 Java끼리 왕복, C는 C끼리. 층 사이의 "의미"를
  보는 테스트가 없었고, 그 사이를 이어야 할 원장 데몬은 값을 읽지 않았다.
- Q. 변이 검사에서 컴파일 오류를 왜 "안 잡힘"으로 치나?
  A. 테스트가 본 것이 아니라 컴파일러가 막은 것이기 때문이다. 다음 변경이 상수 참조를 없애면 그 보호도
  사라진다. 값을 바꾸는 형태로 다시 걸어야 테스트가 일하는지 안다(6.2).

### 3.2 모든 조각이 테스트를 통과했는데 원장 데몬은 무조건 성공을 돌려주고 있었다 (T6-03, T3-15)

**상황**
원장 쪽은 리스너(T3-03)·워커 풀(T3-04)·공유메모리(T3-05)·계좌(T3-06)·검증(T3-07)이, SOR은 전략 4종과
집행기가, 매칭 엔진은 두 시장 규칙이 각자 테스트를 통과했다.

**증상 (감사에서 나온 셋)**
1. `ledgerd`가 **T3-03 때의 껍데기 그대로** 무조건 성공을 돌려줬다. 머리 주석은 "T3-06/07이 들어오면
   연결한다"고 했지만 연결되지 않았다
2. 채널계 원장 포트 기본값이 0이라 그대로 띄우면 **모든 주문이 503**
3. 채널계는 접속 8개를 풀로 재사용하는데 리스너는 **한 번에 한 접속**만 처리 → 동시 주문이 5초 매달렸다
   "확인 필요"로 떨어졌다

**근본 원인**
계좌·검증·SOR·매칭은 각자 통과했지만 **이어 주는 코드가 없었다.** 태스크가 조각 단위로 쪼개져 있었고,
"이어 붙인다"는 일 자체가 어느 태스크의 완료 조건에도 없었다.

**어떻게 찾았나**
T6 감사에서 전 구간을 실제로 빌드·실행·화면까지 확인했다(TASKS.md Phase 6 머리말). 같은 종류의 발견이 이미
T3-15에 한 번 있었다 — 진짜 두 프로세스를 진짜 소켓으로 붙이자 조각 테스트가 하나도 못 잡은 문제 셋이 나왔다:
- `fep/session.h`의 `session_t`(접속 세션)와 `exchange/market_rules.h`의 `session_t`(장 운영 구간) **이름
  충돌**. 각자 테스트는 둘을 한 번역 단위에 놓지 않았다 → exchange 쪽을 `market_session_t`로(쓰임 33 대 51,
  커밋 `336cd7b`)
- `order_t.id`는 호출부가 매긴다 — 엔진이 붙여 줄 줄 알았다. 헤더를 안 읽고 짐작한 대가
- **재기동한 상대의 전문이 전부 중복으로 버려졌다.** 새로 뜬 거래소는 시퀀스를 1부터 시작하는데 우리 기대값은
  이어져 있어 모든 응답이 "이미 본 번호"가 됐다. 접속은 살아 있는데 아무것도 흐르지 않았다. T3-12의 갭 감지가
  만든 사각지대 → 로그인 응답 번호가 기대값보다 **작으면 재기동**으로 본다(크거나 같으면 갭이라 T3-12 동작 유지)

**해결 (T6-03)**
- `ledger_core` 모듈을 새로 만들어 처리 논리를 데몬 밖으로 뺐다 → 소켓 없이 시험
- 주문마다 계좌·증거금 검증(T3-07), 매칭 엔진 2개 + 통합 호가창을 원장 프로세스 안에 둔다. 시장 지정이면 그리로,
  **자동(SOR, `MSG_MARKET_AUTO`=255)이면 BEST_PRICE로 배분**
- 응답에 실제 주문번호·체결 수량·평균 체결가. 체결분은 증거금에서 정산
- 기본 포트 9100, 채널계 접속 풀 1개
- 연결하지 않은 취소·정정은 **가짜 성공 대신 `ERR_NOT_SUPPORTED`** (취소는 T7-01에서 실제로 연결했고, 정정은 지금도 이 답이다)

**대안과 선택 이유**
- **fork 워커를 쓰지 않는다.** 워커마다 매칭 엔진이 따로 생겨 **호가창이 워커 수만큼 갈라진다.** 단일 프로세스·
  단일 스레드로 처리한다 — 결정성 규약과도 맞다. 대가로 T3-04 워커 풀은 이 경로에서 쓰이지 않는다
- 채널계 풀은 그에 맞춰 1로 줄였다(8 vs 단일 접속 리스너였기 때문)
- **정산은 체결 이벤트 콜백 한 곳.** taker 체결과 나중에 오는 maker 체결을 같은 코드가 정산한다. 안 체결될
  수량은 `주문 − 체결 − 살아 있음` 불변식 하나로 푼다
- 방향(최소 연결)은 사용자가 골랐다(TASKS.md Phase 6). FEP를 사이에 둔 다중 프로세스 구성은 T3-15 통합
  테스트로만 검증했다(CLAUDE.md)

**검증**
- 변이 20개 중 19개 잡힘. L13(용량 검사 삭제)은 Debug에서 안 잡히고 **ASan에서 heap-buffer-overflow로 잡힘**
  — 커밋 게이트가 ASan을 돌리므로 남긴다. L18(논리 시각 안 늘림)은 같은 가격 FIFO가 삽입 순서로 이미 정해져
  관찰 불가 — 주석
- 처음 살아남은 L4(maker 체결 매핑)·L9(배분 실패 해제)·L12(지정 시장)를 보고 단건 주문 조회를 구현하고,
  중복 시장 검사를 지우고, NXT 지정 테스트를 더했다
- C 58/58 × Debug·Release·ASan

**배운 것**
- **조각의 통과는 전체의 통과가 아니다.** 같은 교훈이 T5-05에서도 나온다 — "조각의 속도를 전체의 속도로 읽으면
  안 된다"
- 껍데기 코드에 "나중에 연결한다"는 주석만 두면 잊힌다. 연결 안 된 기능은 가짜 성공이 아니라 명시적 거절
  (`ERR_NOT_SUPPORTED`)을 돌려줘야 드러난다

**예상 꼬리 질문**
- Q. 단일 스레드면 처리량이 걱정되지 않나?
  A. T5-05에서 같은 구성(한 프로세스, 7단계)을 재 보니 저널을 끄면 p50 351ns, 1.5M TPS였고, 병목은 스레드가
  아니라 fsync(저널 기록 99.8%)였다. 호가창을 둘로 쪼개는 것보다 하나를 지키는 게 먼저였다.
- Q. 워커 풀(T3-04)과 공유메모리(T3-05)는 그럼 헛일이었나?
  A. 기록상 T6-03은 "워커마다 매칭 엔진이 따로 생겨 호가창이 워커 수만큼 갈라진다"는 이유로 fork 워커를 쓰지
  않았다. 즉 매칭 엔진을 원장 프로세스 안에 넣는 "최소 연결"을 고르면서 T3-04의 사전 fork 구조는 이 실행 경로에서
  빠졌다. 문서에 그 이상의 평가는 없으니 트레이드오프로 솔직하게 말한다(본인 해석이 필요한 자리).
- Q. 재기동을 "번호가 작아졌다"로 판단하면 오판 위험은?
  A. 한 상대의 번호는 커지기만 하므로 더 작은 번호는 "그 번호를 매기던 상대가 더는 없다"는 뜻이고, 그때는
  메울 갭도 없다. 크거나 같으면 갭으로 보고 T3-12 재전송 흐름을 그대로 탄다(T3-15).

### 3.3 변이 검사가 "9/9 잡힘"이라고 거짓말했다 — 검사 도구를 검사하기 (T6-04 외)

**상황**
이 프로젝트는 태스크마다 **변이 검사**(코드를 일부러 망가뜨려 테스트가 실패하는지 확인)를 했다. 통과만 보면
"아무것도 안 잡는 테스트"를 놓치기 때문이다(T1-02에서 `err_str()`을 망가뜨려 본 것이 시작).

**증상 — 도구가 거짓 결과를 낸 사례들**
| 태스크 | 거짓 결과 | 실제 원인 |
|---|---|---|
| T6-04 | Java 변이 **9/9 잡힘**, 너무 빨랐다 | `mvnw.cmd`를 못 찾아 **원본도 실패**. 전부 "잡힘"은 아무것도 못 돌린 결과 |
| T1-09 | 변이가 "안 잡힌 것처럼" 보임 | 변이가 `-Werror` 빌드 실패를 냈는데 **옛 바이너리가 남아** ctest가 통과 |
| T5-03 | R10(매수/매도 부호) "살아남음" | 정규식이 줄바꿈을 못 넘어 **변이가 아예 안 들어감** |
| T3-11 | X6 "살아남음" | 변이가 **잘못된 자리**에 들어감. 손으로 넣으니 잡힘 |
| `486595f` | 모든 변이 "미적용" | Windows git(autocrlf)과 WSL git 방침이 반대라 **작업 트리가 CRLF**, 여러 줄 정규식만 조용히 안 맞음 |
| 인수인계 | 모든 변이 "살아남음" | `/mnt/c` 시계 어긋남으로 **재빌드를 건너뜀** |
| T1-20 | Release에서 전부 통과 | assert 기반 테스트가 **`NDEBUG`로 전부 사라짐** |
| T1-20 | 이중 해제 검사를 통째로 빼도 통과 | `test_order_pool_double_free`가 SIGABRT 핸들러를 깔아 둔 채라 **어떤 assert 실패도 "기대한 abort"로 둔감** |
| T5-02, T5-05 | S7·S8, P1·P5 "잡힘" | 인자가 미사용이 돼 **빌드 실패**로 막힌 것. 테스트가 본 것이 아님 |

**근본 원인**
변이 검사의 판정은 "테스트 명령의 종료 코드가 0이 아니다"다. **실패의 이유를 확인하지 않으면** 환경 오류·빌드
실패·미적용 변이가 전부 "잡힘" 또는 "살아남음"으로 섞인다.

**어떻게 찾았나 (T6-04)**
결과가 **너무 빨랐다.** 원본 코드로 같은 명령을 돌려 보니 원본도 실패했다.

**해결 — 검사 절차에 넣은 규칙**
1. **원본 통과를 먼저 확인**한 뒤 변이를 돌린다(T6-04, 절대 경로로 고침 → 다시 9/9, C 10/10)
2. **빌드 실패를 명시적으로 잡는다.** 빌드 실패로 막힌 변이는 "잡힘"이 아니다 → 값을 바꾸는 형태(`upto_seq + 1`,
   `cap + SNAPSHOT_MAX`)로 다시 건다(T1-09, T5-02, T5-05)
3. **치환이 실제로 먹었는지 `cmp -s`로 확인**(T5-03). 그래도 의도한 자리인지는 모르므로 **살아남은 변이는 적용된
   모습을 눈으로 본다**(T3-11)
4. `.gitattributes`에 `* text=auto eol=lf`(커밋 `486595f`)
5. 복구 뒤 **목적 파일을 지우고** 다시 빌드한다. `touch`는 `/mnt/c`에서 들쭉날쭉. `trap restore EXIT`는 SIGKILL에
   소용없으니 끝나면 `diff`로 원본 대조(인수인계)
6. 테스트 타깃에 `-UNDEBUG` 강제(T1-20). 이중 해제 테스트는 기대한 abort 직후 핸들러를 `SIG_DFL`로 되돌리고
   NDEBUG 계약(무시하되 프리리스트는 멀쩡)까지 검증

**대안과 선택 이유**
Java 쪽에 변이 도구(PIT 등)를 쓰는 기록은 없다. 기록된 방식은 스크립트로 소스를 치환하고 빌드·테스트를 돌리는
수작업 변이다. 그래서 도구의 신뢰를 **절차(원본 선확인·빌드 실패 분리·적용 확인)**로 확보했다.

**배운 것**
- **"전부 잡힘"은 가장 의심해야 할 결과다.** 검증 도구도 검증 대상이다
- "통과했다"가 거짓말이 되는 경로는 생각보다 많다 — NDEBUG, 남은 바이너리, 시그널 핸들러, 줄바꿈, 시계

**예상 꼬리 질문**
- Q. 변이 검사를 왜 굳이 했나? 커버리지로는 부족한가?
  A. 커버리지는 코드가 **실행됐는지**만 말한다. T3-11에서 백오프 상한을 `min=100, max=1600`(정확히 100×2⁴)으로
  둬서 자르는 코드가 한 번도 실행되지 않았고, T1-06에서는 기준가 경계가 우연히 호가 단위에 맞아 반올림 변이가
  안 잡혔다. 이런 건 "테스트가 그 버그를 볼 수 있는가"를 물어야 드러난다(T1-17).
- Q. 살아남은 변이는 다 테스트 구멍인가?
  A. 아니다. 기록에서 다섯 종류로 나눴다 — 진짜 구멍 / 도달 불가능한 방어 / 규격은 요구하나 이 구현에서
  구분 안 됨 / 아무 일도 하지 않는 대입 / 확인할 수 없는데 지우면 안 되는 것. 처분이 각각 다르다(6.2).
- Q. ASan에서만 잡히는 변이는?
  A. T6-03 L13(용량 검사 삭제)은 Debug에선 통과하고 ASan에서 heap-buffer-overflow로 잡혔다. 커밋 게이트가
  ASan을 돌리므로 "잡힘"으로 인정했다. 반대로 T5-01 J3는 넘쳐 쓰는 주체가 libc(`fread`) 안이라 ASan도 못 봤다.

### 3.4 반올림한 평균끼리 뺀 bp가 진짜 차이를 가렸다 — 측정값의 정직성 (T6-07, T6-02, T5-05)

이 프로젝트의 최종 산출물은 측정 결과다. 그래서 **측정이 틀린 것이 가장 비싼 버그**였다. 세 사례를 한 이야기로 한다.

**상황**
시드 30개 품질 리포트(T5-08)에서 BEST_PRICE·SPLIT·SWEEP 세 전략의 KRX_ONLY 대비 분포·승패가 **셋 다 똑같았다.**
T5-08 기록은 "원 단위 평균끼리 빼서일 가능성이 크다(확인은 안 했다)"는 빚을 남겼다.

**증상과 원인 ① — 반올림 (T6-07)**
- `compare.c`가 `eq_avg_price()`(원 단위 버림) 결과끼리 빼고 있었다
- 그런데 같은 프로젝트의 `execution_quality.h`(T2-13)가 "bp는 평균 단가가 아니라 체결 금액에서 직접 낸다.
  10,000원에서 1원은 정확히 1bp — 재려는 크기와 같다"고 경고해 뒀다. 슬리피지는 그 규칙을 지켰는데
  **전략 간 비교에서만 어겼다**
- T2-13의 예: 3주를 30,020원에 체결하면 평균 단가로 내면 6bp, 금액으로 내면 7bp이고 정답은 7bp

**해결 — 어떻게 정밀하게 뺄까 (선택지 셋)**
- (a) `double` → "부동소수를 쓰지 않는다 — 반올림 오차가 누적되면 측정을 믿을 수 없다"에 어긋난다
- (b) 교차곱 `N_a·F_b − N_b·F_a`를 bp로 → 금액 × 수량 × 10000이 int64 한계(9.2×10^18)에 너무 가깝다
- (c) **평균을 1/10000원 정수로 들고 가서 뺀다** ← 채택. 금액 × 10000만 곱하므로 금액 9.2×10^14원까지 안전,
  남는 버림 오차는 0.0001bp
- `eq_avg_diff_bp` 추가, 분모는 기준(a)의 평균

**추측으로 적힌 원인을 확인했더니 절반만 맞았다**
고친 뒤에도 세 전략은 칸마다 같은 승패였다. 일회용 프로그램으로 30개 시드의 **체결 금액 원값**을 찍었다.
- KRX_THIN·NXT_THIN·CROSSED: 세 전략의 체결 금액·수량이 **원 단위까지 완전히 같다**
- BALANCED: 5억 원 중 수십~수천 원 차이(0.01bp 미만)

→ 셋이 같은 것은 **반올림 탓이 아니라 실제 결과**였다(셋 다 양 시장에서 지정가 안의 같은 호가를 다 먹는다).
반올림 결함은 따로 실재했다 — **KRX_THIN의 "1무"는 가짜(→30승), NXT_THIN의 무승부 10개 중 5개는 실은 패배.**
또 리포트의 설명("셋의 차이가 평균 단가의 1~2bp 차이로 나타난다")도 틀렸다. 1~2bp는 **슬리피지**에서 나오고
평균 단가 차이는 0.001bp 수준이다. 사실대로 고쳤다.

**테스트 구멍도 있었다**
- 기본 시드에서는 옛 식과 새 식이 **우연히 같은 값**을 내서, `compare.c`를 옛 식으로 되돌려도 통과할 수 있었다
  → **두 식이 실제로 갈리는 시드를 찾아** 대조하고, 못 찾으면 실패하게 했다
- 부호 검사가 **버린 평균의 대소**로 부호를 요구해, 0.5bp 미만 차이가 0이 되면 틀리게 실패했다 → 체결 금액
  교차곱의 부호로
- 변이 E4(분모를 b로)가 처음엔 살았다. 차이가 몇 bp면 분모가 a든 b든 반올림 결과가 같다 → 20,000 대 10,000
  (5000bp) 케이스로 5/5
- 재생성 결과: 슬리피지·체결률·평균 단가 열은 **그대로**, KRX_ONLY 대비 분포·승패와 설명만 바뀜

**증상과 원인 ② — 판정 이름이 데이터와 반대로 읽혔다 (T6-02)**
- 리포트가 KRX_THIN **29승 0패 1무**와 NXT_THIN **0승 20패 10무**를 둘 다 "엇갈림"으로 판정 → 결론 문장이
  "항상 우위 0, 엇갈림 9". 결론만 읽으면 "SOR 전략은 들쭉날쭉하다", 데이터는 "KRX가 얇을 땐 한 번도 안 지고,
  NXT가 얇을 땐 한 번도 못 이긴다"
- **원인은 버그가 아니라 판단이었다.** T5-08은 "한 번이라도 비기면 항상 우위가 아니다"로 보수적으로 정했고
  그 보수성은 옳았다. 문제는 "항상 우위가 아닌 것"을 전부 "엇갈림"에 몰아넣은 것. **과장을 피하려다 반대
  방향으로 틀렸다**
- 선택지: (a) "항상 우위"를 비김 허용으로 느슨하게 → "항상"이 거짓 / (b) "비김 섞인 우위"를 따로 → 판정 6개,
  결론 문장이 읽기 어려움 / (c) **"항상"을 버리고 일어난 일만 이름으로**: 진 적 없음 / 이긴 적 없음 / 차이 없음
  / 엇갈림 ← 채택. 결론 줄에 승/패/무를 함께 적어 "진 적 없음"을 30전 30승으로 읽지 않게 했다
- 숫자는 하나도 안 바뀐 것을 **전체 diff**로 확인. (처음엔 숫자 열만 뽑아 비교하려다 WSL로 넘기며 awk의 `$1`이
  벗겨져 **빈 출력끼리 비교해 "동일"이 찍혔다.** 믿지 않고 전체 diff로 확인했다)

**증상과 원인 ③ — 0건짜리 보고서가 "TPS 2300만"을 냈다 (T5-05)**
- 주문 가격을 기준가 +15원으로 뒀는데 5,000~20,000 구간 호가 단위가 10원이라 **2만 건이 전부 원장에서 거부**
- 프로그램은 성공으로 끝나고 "TPS 2300만" 표를 냈다 — 거부 루프의 속도였다
- 해결: 측정 건수가 0이면 어느 단계에서 몇 건이 왜 떨어졌는지 찍고 **실패로 끝낸다**, 거부 건수를 보고서에 적는다
- 같은 종류의 실수 한 번 더: 주문 가격을 코드와 보고서 문구에 따로 적고 한쪽만 고쳐 **조건이 틀린 보고서**가 나옴
  → `AGGRESSION` 상수 하나로 묶었다

**배운 것**
- **추측으로 적은 원인은 확인 전까지 원인이 아니다.** 확인해 보니 절반만 맞았고, 나머지 절반은 리포트 설명까지 틀리게
  만들고 있었다
- **숫자가 그럴듯하면 아무도 "측정된 건수: 0"을 안 본다.** 측정 도구는 자기가 0건을 쟀을 때 실패해야 한다
- **조건이 틀린 보고서는 숫자가 맞아도 근거가 아니다**(T5-05)

**예상 꼬리 질문**
- Q. 왜 평균을 안 쓰고 중앙값·승패를 썼나?
  A. 평균 +2bp는 "30번 모두 +2"와 "29번 +5에 한 번 −85"를 구분하지 못한다(T5-08). 짝수 개면 가운데 둘 중
  **낮은 쪽** — 평균을 내면 어느 시드에도 없던 숫자가 되고, 낮은 쪽이면 개선폭을 부풀리지 않는다.
- Q. 한 시드 결과(T2-14)와 30시드 결과가 달랐나?
  A. 달랐다. 시드 20260916 표는 BALANCED에서 +5bp였지만 30개 중에서는 중앙값 +2bp, 최종 22승 5패 3무다.
  T2-14 리포트가 적어 둔 "한 시드의 한 장면이다"가 맞았다(T5-08, T6-07).
- Q. NXT_THIN에서 SOR이 KRX_ONLY보다 비싸게 샀는데 SOR이 나쁜 건가?
  A. 아니다. 더 많이 채우느라(체결률 중앙값 57.63% vs 52.31%) 비싼 호가까지 갔다. 단가와 체결률을 따로 보면
  오독한다. 그래서 표에 둘을 나란히 두고, 화면(T6-09)에서도 슬리피지 "+1bp"와 KRX_ONLY 대비 "−1bp"에 이름을
  붙였다.

### 3.5 fsync 하나가 전 구간을 7,572배 느리게 했다 — 그래도 남겼고, 장애 주입으로 검증할 수 없는 경계도 알았다 (T5-01, T5-05, T5-04)

**상황**
T5-01에서 입력 저널(append-only)을 만들며 **매 레코드 `fsync`**를 기본으로 정했다. 이 저널의 쓰임이 "재기동 뒤
되살리기"라 잃으면 안 되기 때문이다. 값이 얼마인지는 재지 않았다.

**측정 (T5-05, `pipeline-2026-09-16.md`)**
| | 저널 끔 | 저널 켬 |
|---|---:|---:|
| 전 구간 p50 | 351 ns | 2,657,903 ns (7,572배) |
| TPS | 1,534,801 | 376 |
| 가장 비싼 단계 | SOR 계획 178ns (50.7%) | **저널 기록 99.8%** |

- **fsync의 비용은 자기 단계에 머물지 않는다.** 저널을 켜자 매칭도 50ns → 1,043ns. 저널을 쓰는 동안 프로세스가
  내려갔다 오면서 캐시가 식는다. "저널만 빼면 나머지는 그대로"로 읽으면 안 된다
- **분위수는 더해지지 않는다.** 단계별 p50 합과 "전 구간 합" p50이 다르다 — 보고서에 못 박았다
- 모든 주문이 한 다리(BEST_PRICE)였다는 것도 보고서에 적었다. 변이 P6(다리별 시간 누적)이 살아남은 이유를 파다가
  "매칭·체결 반영 숫자는 한 시장에 보낸 주문의 비용"이라는 해석 조건이 빠져 있음을 알았다

**판단 — 바꾸지 않는다**
- 376 TPS는 이 프로젝트의 목표(전략 비교)에 모자라지 않는다. T5-01의 이유("잃으면 안 되는 기록")는 표를 보고도 그대로
- 바꿀 때의 선택지는 셋이고 **셋 다 내구성을 깎지 않고 지연을 옮기는 방법**이다: 그룹 커밋 / 저널 전용 스레드 /
  배터리 백업 캐시 장치
- **재기 전에 고르지 않는다.** "묶으면 빠르지만 묶은 만큼이 통째로 사라질 수 있다"(T5-01)

**T5-01의 다른 설계**
- **입력만 적고 결과는 적지 않는다.** 엔진이 결정적이라 입력만으로 결과를 다시 만든다. 결과까지 적으면 양이 몇 배고
  **진실이 둘이 된다** — **결정성이 이 선택을 가능하게 한다**
- **CRC를 둔다(T3-01 전문과 반대).** 전문은 TCP가 지켜 주지만 파일은 쓰다 죽으면 반쪽이 남고 아무도 막아 주지 않는다.
  CRC는 머리와 바디 모두를 덮는다 — 길이 필드가 깨지는 것이 가장 위험하다
- **찢어진 꼬리는 버리고 고치지 않는다.** 반쪽에서 나머지를 지어내는 것은 없던 입력을 만드는 일
- 테스트는 **바이트 단위 절단 전수** — 모든 자리에서 잘라 보고 읽힌 레코드 수와 찢어짐 여부를 정확히 확인

**장애 주입으로 확인한 것 (T5-04)**
"뒷모습을 흉내 낸 것과 실제로 일어난 것은 다르다" — T5-01은 손으로 자른 파일, T5-02는 손으로 만든 `.tmp`였다.
그래서 자식 프로세스를 **실제로 `SIGKILL`**했다.
- fsync까지 끝났다고 자식이 약속한 37건이 SIGKILL 뒤에도 그대로
- 스냅샷을 쉬지 않고 쓰는 자식을 40회 다른 시점에 죽임 → **원래 자리가 반쪽인 적 0회.** 21~29회는 `.tmp`가 남아
  실제로 쓰는 도중에 죽은 것
- 60KB 레코드를 쉬지 않고 적게 하자 **꼬리가 실제로 찢어짐**(25회 중 3~4회), 약속한 건수는 그대로
- 스냅샷 + 이후 저널로 되살린 합이 다시 계산한 합과 정확히 같고 T5-03 대사를 통과

**디버깅 포인트**
- **처음엔 한쪽 가지만 보고 있었다.** 자식이 한 바퀴 돌기를 기다린 뒤 죽이니 "옛 스냅샷으로 남는" 경우가 40회 중
  0회 — `rename`이 지키는 바로 그 가지가 시험되지 않았다. 앞 절반은 기다리지 않고 죽이도록 고치니 3~4회가 그 가지로
- 경쟁: 자식 진행 수를 **죽이기 전에** 읽으면 그 사이에 더 쓸 수 있어 상한이 틀린다 → 죽은 뒤에 읽는다

**장애 주입이 닿지 못한 곳 — 변이로 드러났다**
변이를 **이 테스트가 지킨다고 주장하는 생산 코드**에 걸었다. 7종 중 4종 잡힘.
- **`fsync`를 빼도 통과(F2·F3), `fflush`를 빼면 잡힘(F4).** `fflush` 버퍼는 프로세스 안에 있어 함께 사라지지만,
  `fsync`가 미는 커널 페이지 캐시는 프로세스가 죽어도 남는다. **프로세스를 죽이는 것과 전원을 끊는 것은 다르다.**
  T5-02 S12에서 짐작만 했던 것을 여기서 실제로 확인
- **저널 CRC 검사를 빼도 통과(F7).** 죽은 쓰기는 **짧은** 레코드를 남기지 **온전하되 틀린** 레코드를 남기지 않는다.
  짧은 것은 길이 검사가 먼저 잡는다. CRC가 지키는 것은 나중에 썩는 비트와 깨진 길이 필드
- 셋 다 테스트 구멍이 아니라 **이 방법으로는 닿을 수 없는 곳**이다. 테스트 머리말에 경계를 적었다 — 안 적으면 다음
  사람이 "장애 주입이 있으니 괜찮다"고 믿는다

**배운 것**
- 내구성 선택은 **재고 나서도 유지할 수 있어야** 선택이다. 값을 몰랐던 것과 알고 고른 것은 다르다
- 검증 방법마다 **닿는 범위**가 있다. SIGKILL은 프로세스 메모리 유실까지만 시험한다

**예상 꼬리 질문**
- Q. 전원 유실은 어떻게 시험하나?
  A. 이 프로젝트는 하지 않았다. 기록된 사실은 "SIGKILL로는 fsync 유무가 구분되지 않는다"는 것까지다. 선택지를
  말하자면 가상 머신 강제 종료나 블록 장치 수준의 쓰기 유실 흉내가 필요하다 — 이건 기록에 없는 일반론으로 구분해 말한다.
- Q. 스냅샷은 왜 임시 파일 + `fsync` + `rename`인가?
  A. 원래 자리에 바로 쓰다 죽으면 반쪽 스냅샷이 남고, 스냅샷은 이어 붙인 기록이 아니라 통째로 하나의 상태라 "찢어진
  꼬리를 버린다"가 안 통한다. 임시 파일을 **같은 디렉터리**에 두는 이유는 다른 파일 시스템으로 넘어가면 `rename`이
  원자성을 잃기 때문이다(T5-02).
- Q. 스냅샷이 깨지면?
  A. 저널이 진실이고 스냅샷은 시간을 줄이는 것이라 **버리고 처음부터 재생**한다. 느릴 뿐 틀리지 않는다. 다만
  `snapshot_bad`로 그 사실을 숨기지 않는다 — 성능이 조용히 무너져도 모르면 안 되니까. `upto_seq`는 필수다. 모르면 같은
  주문을 두 번 반영하거나 스냅샷 이후가 사라진다(T5-02).

### 3.6 같은 종류의 빈틈이 세 번 나왔다 — 그리고 재현하지 못한 경합을 리뷰로 찾았다 (T6-03, T6-04, T6-10, T6-11)

**상황**
Phase 6에서 오류를 고친 뒤 "처음부터 다시 점검"을 반복했다. 두 번째 바퀴에서 두 가지를 더 찾았다.

**증상 1 — 원장 끊김 표시가 한 번도 켜지지 않았다 (T6-10)**
T4-05의 완료 조건 "원장이 끊기면 화면에 그 사실이 보인다"에 맞춰 `ledger-down` 이벤트, 화면의 "원장 끊김" 표시,
테스트까지 있었다. 그런데 **운영 코드 어디서도 그 이벤트를 보내지 않았다.** 테스트는
`hub.broadcast(StreamEvent.ledgerDown(...))`를 직접 불러 통과했다.

**근본 원인 — 부품의 테스트가 부품을 직접 부른다**
T6-03(무조건 성공하던 원장 데몬), T6-04(`broadcast()`를 부르는 곳이 없던 방송)와 **같은 모양**이다.
부품마다 테스트는 있는데, 부품을 **잇는 줄**을 보는 테스트가 없었다. 부품 테스트가 부품을 직접 부르면
줄이 없어도 초록불이다.

**어떻게 찾았나**
"이벤트를 만드는 함수"마다 "부르는 운영 코드"를 짝지어 셌다. `ledgerDown()`을 부르는 곳이 0이었다.

**해결과 판단**
- 원장을 부르는 두 곳(1초마다 호가를 읽는 `BookController`, 주문의 `OrderService`)이 결과를
  `StreamHub.ledgerReachable(up, why)`에 알린다
- **바뀔 때만 방송한다.** 화면이 1초마다 호가를 읽으므로 실패마다 보내면 초마다 알림이 쌓인다.
  대신 바뀐 뒤 들어온 구독자는 방송을 놓치므로 접속할 때 현재 상태를 따로 보낸다
- 테스트는 이제 **줄을 지나간다**: 원장 포트에 아무도 없는 컨텍스트에서 `GET /api/book`을 부르면 구독자가
  `ledger-down`을 **한 번만** 받고, 늦게 들어온 구독자도 받는다
- 변이 6개(알림 호출 셋 삭제, 매번 방송, 늦은 구독자 누락, 회복 누락) 6/6 잡힘

**증상 2 — 크기 1인 접속 풀이 접속을 둘 만들 수 있었다 (T6-11)**
Phase 6 변경분을 새 눈(리뷰 에이전트)으로 읽게 했다. 돈 계산·전문 배치에서는 결함이 없었고, 풀에서 나왔다.
`borrow()`가 "살아 있는 수 < 상한"을 **본 뒤에** 수를 올렸다(check-then-act). 두 스레드가 함께 검사를 통과하면
접속이 둘이 된다. 원장은 접속을 한 번에 하나만 받으므로 **두 번째 접속의 주문은 원장의 수락 대기열에 갇혀**
"확인 필요"가 되고, 첫 접속이 닫히는 한참 뒤 **옛 가격으로 체결될 수 있다.** 화면은 KRX·NXT 호가를 동시에
읽으므로 첫 화면을 열 때마다 이 경합의 조건이 생긴다. 같은 리뷰가 "버려진 접속은 기다리던 요청을 깨우지 않는다"와
"화면이 `outcome` 없는 응답(예: 500)에서 통째로 멈춘다"도 찾았다.

**재현한 것과 재현하지 못한 것을 나눠 적었다**
- 대기자 문제: 테스트를 먼저 쓰니 고치기 전 코드에서 **3초를 다 기다린 뒤 "모자라다"로 실패** — 재현됨
- 접속 둘 경합: 창이 명령 몇 개 폭이라 **32스레드 한 판, 16스레드 200판으로도 재현되지 않았다.** 코드를 읽어
  확정했고, 테스트는 회귀 방지용으로 남겼다. 원장 쪽 접속 수는 수락 스레드가 늦게 세서 판을 넘어 섞이므로,
  판마다 **건네진 접속 객체의 개수**를 세는 방식으로 바꿨다
- 면접에서 "재현했나?"라고 물으면 **"못 했다, 그래서 이렇게 확정했다"** 가 정직한 답이다

**대안과 선택 이유**
- (a) `AtomicInteger.getAndUpdate`로 검사와 증가를 붙인다 → 경합은 막지만 **대기자를 깨우는 일**은 따로 짜야 한다
- (b) **세마포어(허가증 N장)** ← 채택. 빌리기 전에 허가를 잡고, 돌려주든 버리든 `release()`에서 푼다.
  푸는 순간 기다리던 요청이 깬다 — 두 문제를 한 장치로

**변이 검사가 한 번 더 일했다**
세마포어로 바꾼 뒤 변이 P3("접속을 만들다 실패하면 허가를 안 돌려놓음")가 **살아남았다.** 그대로면 원장이
한 번 죽는 것만으로 크기 1 풀의 허가가 영영 사라져, 원장이 살아나도 계속 "모자라다"가 된다. 원장이 죽은
상태에서 두 번 빌려 **두 번째도 곧바로 "붙을 수 없다"로** 실패하는지 보는 검사를 더해 3/3.

**마지막 확인 — 진짜로 죽였다 살렸다**
채널계·화면을 띄운 채 `ledgerd`를 죽이자 화면에 "원장 끊김", 다시 띄우자 표시가 사라지고 호가창이 시드 상태
(NXT 70,000원 2,257주)로 돌아왔으며, 바로 낸 SOR 매수 100주가 전량 체결됐다.

**배운 것**
- "테스트가 있다"와 "그 기능이 이어져 있다"는 다르다. **이벤트·콜백을 만들면 부르는 곳을 세어 본다**
- 동시성 버그는 테스트로 재현이 안 될 수 있다. **읽어서 확정하고, 재현 못 했다고 적는다**
- 고친 코드에도 변이를 건다 — 새 장치(세마포어)의 실패 경로가 곧바로 구멍이었다

**예상 꼬리 질문**
- Q. 왜 처음부터 세마포어를 안 썼나?
  A. 처음 풀(T4-03)은 크기 8이었고 "상한을 넘기지 않는다"를 64건 × 8스레드로 시험했다. 넘친 접속 하나가
  큰 문제가 되지 않는 구조였다. 크기를 1로 줄이고(T6-03) 원장이 접속을 하나만 받게 된 순간 **같은 경합의 값이
  달라졌다** — 넘친 접속이 곧 갇힌 주문이 됐다. 설계 조건이 바뀌면 옛 판단을 다시 봐야 한다.
- Q. 풀 대신 요청마다 접속하면?
  A. 원장이 접속을 하나씩 끝까지 처리하므로 여전히 줄은 서지만, 접속 비용이 주문 지연에 얹힌다(T4-03 판단).
  근본 해결은 원장이 여러 접속을 한 스레드로 받는 이벤트 루프(T3-08 구조)로 가는 것이다.
- Q. 리뷰 에이전트를 믿었나?
  A. 지적마다 해당 줄을 직접 읽어 확인했고, 재현 가능한 것은 실패하는 테스트로 먼저 재현했다.

### 3.7 화면의 1원 차이가 34,887원 누수였다 — 주석의 "총량은 맞는다"를 확인하기 (T7-07)

**상황**
T7-04에서 화면을 원장 상태에 연결하고 브라우저로 기능을 하나씩 눌러 보던 중이었다. 주문 상세(T7-02)가 생기면서
같은 주문의 평균가를 **두 곳**에서 볼 수 있게 됐다 — 주문 접수 응답과 주문 상세.

**증상**
72,326주 매도 한 건의 **접수 응답 평균가는 69,728원, 주문 상세 평균가는 69,727원**이었다.

**처음 떠올린 원인과 확인**
반올림 차이로 보였다. 하지만 원장·채널계 모두 **버림**이었다 — 같은 규칙이면 같은 금액에서 다른 값이 나올 수 없다.
손으로 체결을 더하니 5,043,169,700원(평균 69,728원). **상세의 체결 금액이 34,887원 모자랐다.**

**근본 원인**
- 매칭 결과의 체결 목록은 `EXEC_FILLS_MAX`(64)건에서 잘린다
- `record_fills()`(`sor/src/executor.c`)는 체결을 건별로 매핑에 옮기는데, 잘린 뒤의 몫만은 **평균 단가 하나(버림)**로
  넣었다. 나눗셈 나머지만큼 금액이 사라진다
- 주석은 "집계값은 정확하므로 총량은 맞는다"였다. 결과 쪽 집계는 정확했지만 **매핑 쪽 총량은 맞지 않았다**
- 이 함수가 건별로 옮기는 이유 자체가 T2-10의 "평균으로 뭉치면 금액이 샌다"였다. 같은 버그가 예외 경로에 남아 있었다

**영향 범위를 따로 확인했다**
예수금은 체결 사건마다 정산하므로 맞았다(5,489,368,500원을 손으로 확인). 틀린 것은 주문 상세의 체결 금액과 그 평균가뿐이었다.

**해결**
남은 몫을 "평균(버림) 가격 몫"과 "1원 높은 몫"으로 나눠 넣는다. 남은 금액 ÷ 남은 수량의 나머지를 1원 높은 쪽 수량으로 두면
합이 정확히 맞는다.
- 시험: 70주 @10,000 + 3주 @10,010을 한 번에 사서 목록을 자르고, 매핑 금액 = 결과 금액. 잘린 뒤 9주(6주 @10,000 + 3주 @10,010 =
  90,030원)를 평균 하나로 넣으면 10,003 × 9 = 90,027원이다. **고치기 전 실패를 확인했다**
- 변이 4개(1원 높은 몫의 가격, 나머지 계산, 두 몫 각각 빠뜨림) 모두 잡힘. C 58/58 × 3빌드

**배운 것**
- **같은 값을 두 길로 보여 주면 불일치가 버그를 드러낸다.** 접수 응답과 상세가 따로 계산했기 때문에 1원이 보였다
- **"총량은 맞는다"는 주석도 확인 대상이다.** 어느 쪽의 총량인지까지 따져야 한다
- 이 프로젝트의 산출물이 평균 체결 단가라서, 1원은 반올림 잡음이 아니라 측정의 정직성 문제다(3.4와 같은 교훈)

**예상 꼬리 질문**
- Q. 왜 목록을 64건에서 자르나? 늘리면 되지 않나?
  A. 매칭 결과(`exec_result_t`)의 체결 목록은 `EXEC_FILLS_MAX` 크기의 고정 배열이고, 총 체결 수량·금액은 잘려도 정확하게 따로 센다(`match.h`).
  기록에 목록 크기를 바꾸자는 판단은 없다. 고정 크기인 한 어떤 크기든 더 큰 주문에서는 잘리므로 잘린 경로가 정확해야 한다 —
  이것은 기록에 없는 일반론으로 구분해 말한다.
- Q. 테스트는 왜 그동안 못 잡았나?
  A. 매칭 엔진 시험(`test_match_limit.c`)은 목록이 잘려도 집계가 정확한지 봤지만, 잘린 목록을 **매핑으로 옮기는** sor 쪽 시험은
  T7-07 전에 없었다. 화면에서 7만 주를 쓸어 담는 주문을 내고, 두 길로 계산한 평균가를 나란히 보고서야 드러났다.

| 문제 | 원인 | 해결 |
|---|---|---|
| 403 본문이 로그에 깨진 바이트로 남았다 | 토스 앞단이 본문을 **gzip**으로 돌려주는데 JDK `HttpClient`는 `Content-Encoding`을 스스로 풀지 않는다 | 바이트로 받아 헤더와 gzip 매직(`1f 8b`)을 보고 푼다. **성공 응답이 gzip이면 토큰 파싱이 통째로 실패했을 자리**라 표시 문제가 아니었다 |

### 5.1 매칭 엔진·자료구조

**D-01. 주문 풀 — 사전 할당, 프리리스트 `next[]`가 사용중 표시 겸용** (T1-04)
- 선택지: 별도 플래그 배열 / 프리리스트 순회로 이중 해제 검사 / `next[]`에 `SLOT_IN_USE(-2)`
- 고른 것: `next[]` 겸용
- 이유: 핫 패스 malloc 금지. 이중 해제를 O(1)에 잡는다. 순회는 해제마다 O(n)
- 이중 해제는 내부 버그라 assert, 그러나 `void` 반환이라 NDEBUG에서 방어가 사라지므로 **조기 반환도 같이**("조용한 자료구조 손상이 크래시보다 나쁘다")
- 포기: `client_order_id`를 문자열이 아닌 `uint64_t`로 — 실제에 덜 가깝지만 구조체가 작아 호가창 순회에 유리

**D-02. 가격 레벨 — 침략적(intrusive) 이중 연결 리스트** (T1-05)
- 선택지: 별도 노드 구조체 / 링크를 `order_t` 안에
- 고른 것: 침략적
- 이유: 노드 풀이 하나 더 안 생기고, `book_remove(book, order)`가 주문에서 노드를 역으로 찾을 인덱스가 필요 없다
- 포기: 한 주문이 한 리스트에만 — 주문은 실제로 한 레벨에만 속하므로 손해 아님
- 부수 판단: `reduce_qty`는 `qty`가 아니라 `filled_qty`를 늘린다(원 수량 보존 = 평균 체결 단가 계산 가능)

**D-03. 호가창 — 가격을 호가 단위로 접은 배열 인덱스** (T1-06)
- 선택지: 원 단위 배열 / 호가 단위 배열(구간 기술자 최대 8개)
- 고른 것: 호가 단위
- 이유: 기준가 100만 원이면 원 단위 28.8MB, 호가 단위 29KB. "최적화가 아니라 배열이 성립하느냐의 문제". 변환은 구간 스캔(≤8) + 나눗셈으로 O(1)
- 포기: 틱보다 세밀한 가격 표현 불가 → 중간가 반올림이 필수가 됨(ADR-0003)
- 최우선호가 캐시: 삽입 시 비교 한 번, 제거 시 빈 최우선일 때만 선형 재계산(병목이면 비트맵, 코드에 표시)

**D-04. 주문 인덱스 — 오픈 어드레싱 + 선형 탐사 + 역방향 시프트 삭제** (T1-07, ADR-0001)
- 선택지: A 체이닝 / B 오픈 어드레싱 + 톰스톤 / C 오픈 어드레싱 + 역방향 시프트(Knuth 6.4 R)
- 고른 것: C
- 이유: 체결·취소마다 항목이 빠지는 표. 톰스톤은 탐사 길이를 단조 증가시키고 되돌리는 재해시는 핫 패스 할당. 체이닝은 노드 풀이 하나 더
- 크기 고정(부하율 0.5, 2의 거듭제곱), 해시 splitmix64(연속 주문번호가 뭉치지 않게, 시드 없음), **순회 API 없음**(해시 순서 의존 → 결정성 깨짐)
- 포기: 삭제 코드 약 20줄 추가, 메모리 두 배(10만 건 4MB)

**D-05. 시장 규칙 — 함수 포인터 테이블 `market_rules_t`** (T1-13, ADR-0002)
- 선택지: A 엔진 안 `market_t` 분기 / B 시장별 엔진 두 벌 / C 함수 포인터 테이블
- 고른 것: C
- 이유: **측정의 신뢰성.** 엔진이 두 벌이면 두 시장 결과 차이에 구현 차이가 섞인다. A는 분기를 빠뜨려도 컴파일되지만 C는 빠진 자리가 NULL이라 즉시 터진다
- `is_open`/`can_submit` 분리(NXT 휴장: 열려 있지 않지만 취소 가능), 가격 결정 `resolve_price`까지 테이블에(엔진에 중간가 분기가 생기지 않게)
- 불변조건: `exchange/src/match/` 아래 `MARKET_` 분기 0
- 포기: 호출당 간접 호출 최대 5회, 인라인 불가

**D-06. 중간가 주문 — 항상 내림, 접수 시점 고정, 한쪽 공백 거부, 가격 정정 불가** (T1-16, ADR-0003)
- 반올림 선택지: 항상 내림 / 항상 올림 / 편별 유리 / 편별 불리 → **항상 내림**. 편별이면 10,000/10,010에서 매수 10,000·매도 10,010이 되어 **중간가끼리 영원히 못 만남**
- 재계산 선택지: 접수 시점 고정 / 지속 갱신 → **고정**. 지속 갱신은 (1) 요청 안 한 이동의 우선순위 (2) 이동이 중간값을 바꾸는 연쇄의 수렴 (3) 재계산 순서의 결정성이 정의되지 않음
- 한쪽 공백: 반대편 호가·기준가 대체 대신 **거부** — 중간가 아닌 가격을 중간가라 부르지 않는다
- 포기: 스프레드 한 틱이면 가격 개선 없음, 실제 NXT와 다를 수 있음(단순화 명시)

**D-07. FOK — 먼저 세고 실행** (T1-10)
- 선택지: 부분 체결 후 되돌리기 / 사전 계수
- 이유: 되돌려도 뗀 상대 주문이 큐 뒤로 가 **시간 우선순위가 복원되지 않는다.** `book_qty_up_to`는 레벨을 직접 훑어 깊이 상한이 없다(스냅샷 버퍼는 상한이 생김)

**D-08. 정정 시 매칭하지 않음, 교차 가격 정정은 거절** (T1-11)
- 이유: 교차한 채 두면 호가창 불변조건이 깨지고, 매칭을 붙이면 범위 초과. 우선순위 상실은 "떼었다 뒤에 붙이기"로(큐 위치 = 우선순위). 완료 주문 취소 불가에 상태 플래그를 두지 않음 — 이미 인덱스에서 빠져 `ERR_NOT_FOUND`가 저절로 나온다(상태와 자료구조가 어긋날 여지 제거)

**D-09. 체결 목록 고정 배열(64) + 넘치면 목록만 잘림, 집계는 정확** (T1-08)
- 이유: 평균 체결 단가가 산출물이라 집계가 잘리면 안 된다. 엔진이 풀·인덱스·호가창을 모두 소유(전량 체결된 상대 슬롯을 누가 돌려주는지 모호함 제거)

**D-10. 난수 xorshift64* + 시장별 splitmix64 파생 시드, 뽑는 순서가 재현성 계약** (T1-17, T1-18)
- `rand()` 거부 이유는 품질이 아니라 **전역 상태**(두 시장 생성기가 서로의 수열에 영향)
- 같은 시드를 두 시장에 주면 같은 주문을 내서 시나리오가 차이를 못 만든다
- "얇다"를 도착률 하나로 표현하지 않음 — 도착률·감쇠·수량 범위 세 축

**D-11. 에러 코드·전문 종별을 X 매크로 목록 하나로** (T1-02, T3-02)
- 이유: 열거형과 문자열 테이블(또는 종별·이름·길이)을 따로 두면 추가 시 한쪽을 빠뜨리고, 누락은 "모르는 종별"로 조용히 거절된다

### 5.2 SOR·측정

**D-12. 통합 호가창에 캐시를 두지 않는다** (T2-01, T2-02, ADR-0004)
- 선택지: A 캐시 + 변경 시 갱신 / B 매번 시장 호가창에 묻기
- 고른 것: B
- 이유: 시장 최우선호가는 T1-06에서 이미 O(1) 캐시. 통합 뷰는 캐시된 값 둘을 비교할 뿐. 얻는 것(배열 접근 한 번 vs 비교 두 번)에 비해 잃는 것(체결·취소·정정 중 알림을 빠뜨린 경로 = 조용한 오답 = 측정 오염)이 크다
- 결정을 지키는 테스트(T2-02): 체결·취소·정정 직후 새 값. 캐시를 몰래 들이면 깨진다
- 동률 규칙: 가격 → 잔량 → 시장 열거 순서, `better()` 하나에 모음
- 포기: 읽을 때 시장 수만큼 호출, `cons_snapshot` 비용이 가장 큼

**D-13. 최선집행 점수 — 정수 0~10000, 가격·비용 모두 1bp당 100점, 가중치 40/30/20/10** (T2-03, T2-04, ADR-0005)
- 정수 이유: 부동소수는 최적화 수준·FMA·x87 80비트에 따라 마지막 비트가 달라져 근소한 총점에서 순위가 **재현 안 되는 형태로** 뒤집힌다
- 같은 계수 이유: "수수료 1bp 싸고 가격 1bp 불리"는 정확히 무승부여야 한다. **가중치는 중요도를 조절하지 단위를 맞추는 도구가 아니다.** 스프레드는 1bp당 20점(다음 체결의 위험 신호)
- 체결 가능성 30: 못 채운 잔량은 다음 호가로 넘어가는 **"지연된 가격"**
- 제외된 시장도 `eligible=false`와 이유를 남김, 항목별 점수 보관(최선집행은 근거를 남기는 의무)
- 설정 파일: 적지 않은 키는 기본값, **모르는 키는 거절**, 검증은 다 읽은 뒤 한 번(줄 순서 의존 방지)
- 포기/한계: 수수료 KRX 3bp / NXT 2bp는 **차이를 만들기 위한 가정**이지 실제 수치가 아님

**D-14. 전략은 주문을 보내지 않고 계획만 만든다** (T2-05)
- 이유: 네 전략을 같은 유동성에서 비교(계획은 호가창을 안 건드려 집행 없이 검증 가능), SWEEP도 통합 호가창만 보고 미리 계산 가능, 적응형 전략은 범위 밖
- `plan_validate()` 불변조건: 다리 합 = 원 수량, 한 시장에 다리 하나, 0주 다리 없음
- KRX_ONLY를 기준선으로: NXT는 KRX 상장 종목 중 일부만 거래 → 모든 종목에 성립하는 건 KRX뿐

**D-15. BEST_PRICE는 쪼개지 않는다, 즉시 체결 시장이 없어도 버리지 않는다** (T2-06)
- 이유: 미리 쪼개면 세 전략이 같은 일을 해 "쪼개는 게 이득인가"를 비교 못 함. 조용한 장에서 거부하면 **라우팅 품질과 무관한 이유로 BEST_PRICE만 체결률이 떨어져** T2-14 비교를 오염. 등록 시장은 `plan_resting_market()`(유리한 상대 호가 → 호가 있는 시장 → 열거 순서)

**D-16. SPLIT — 지정가 안 물량 비례, 최대 나머지(Hare quota)** (T2-07)
- 이유: 지정가 밖 물량은 이 주문에 없는 것과 같다. 최대 나머지는 비례를 가장 적게 왜곡(3주를 47:53으로 나눌 때 단수 하나가 33%씩 움직임). 최소 1주(2014년 이후 1주 단위)

**D-17. SWEEP — "유리한 시장"을 평가 점수가 아니라 가격으로** (T2-08)
- 이유: 평가는 주문 전체의 시장 단위 판단, SWEEP은 호가 단위 판단. 점수에 수수료·스프레드가 섞여 가격 순서를 뒤집을 수 있고, 체결 가능성 항목이 소진 중 매번 바뀐다. 시장별 합산 후 다리 생성, 깊이 64단 제한(한계 표시)

**D-18. 물리 주문번호 = `logical × 16 + market + 1` 산술** (T2-09)
- 선택지: 해시 테이블 / 자리값 인코딩
- 이유: 한 논리 주문은 시장당 다리 하나라 (논리번호, 시장) 쌍이 유일. 양방향 조회가 나눗셈 한 번, 번호만 보고 시장을 앎, 시장 간 번호 비충돌이 구조적으로 보장
- 포기: 논리번호 상한 `UINT64_MAX / 16`(10^18 규모, 실질 제약 아님). 논리 주문은 지우지 않음(이력 보존, 삭제 없는 단순 해시)

**D-19. 분할 주문 — 한쪽 거부·취소 실패 시 되돌리지 않는다** (T2-10, T2-11)
- 이유: 두 거래소는 서로 다른 트랜잭션. 체결된 40주를 없애려면 반대매매 = **새로운 손실 있는 거래**. 취소를 되돌리면 큐 자리를 잃고 그 사이 체결 위험, 반면 실패한 취소는 재시도가 안전. 한 다리라도 접수되면 논리 주문은 거부가 아니다
- `unfilled_qty`(원 − 체결)와 `working_qty`(살아 있는 것)를 분리, 체결이 한 주라도 있으면 상태는 PARTIAL, 거부와 취소를 가르려 `accepted` 필드
- 포기: 쪼갠 FOK는 다리 안에서만 전량-아니면-전무

**D-20. 집행 품질 기준가 = 접수 시점 통합 최우선 상대호가(arrival price)** (T2-13)
- 선택지: (a) 지정가 (b) 중간가 (c) 접수 시점 통합 최우선 상대호가
- 고른 것: (c)
- 이유: (a)는 지정가를 보수적으로 적기만 해도 좋아 보임 — **잣대가 측정 대상에 조종당함**. (b)는 한쪽 호가가 비면 정의 불가(이 시뮬레이터에 흔함). 시장별 기준가는 전략마다 다른 잣대. 집행 뒤 호가는 그 집행이 밀어 놓은 결과라 순환
- bp 반올림은 **0에서 먼 쪽**(버림은 0.6bp 손해를 0bp로 보고), bp는 **체결 금액에서 직접**, 슬리피지는 불리할수록 양수

**D-21. 전략 비교 — 전략마다 엔진을 새로 만들고 같은 시드로 재충전, 매수만, 세션 규칙 없음, 날짜 인자** (T2-14)
- 이유: 같은 호가창에 차례로 돌리면 순서 측정. 매수·매도 평균을 합치면 상쇄. 세션을 걸면 개장 시간이 단가 차이에 섞임. 시스템 시각을 읽으면 같은 시드 산출물이 달라짐
- 포기: CROSSED에서 밀린 시장이 불리한 쪽으로만 나타남

**D-22. 품질 리포트 — 평균 대신 중앙값·최소·최대·승패, 짝수면 낮은 쪽, 판정은 문자 그대로 참인 이름** (T5-08, T6-02)
- 3.4 참조

**D-23. 두 평균의 bp 차이 — 1/10000원 정수 평균** (T6-07)
- 선택지 double / 교차곱 / 1/10000원 정수 → 3.4 참조

**D-24. 벤치 — 평균 대신 분위수, 예열 2만 건 버림, 싱크 없음, 측정 조건을 결과 파일에** (T1-20)
- 이유: 비용이 균일하지 않아 평균이 꼬리를 감춤. 빈 호가창 주문은 유난히 싸서 TPS를 부풀림. 조건 없는 숫자는 비교 불가

### 5.3 전문·원장·FEP

**D-25. 전문 헤더 — 필드별 바이트 직렬화, 빅엔디언, 체크섬 없음, 길이 선행, 바디 64KB 상한, 판 불일치 거절** (T3-01)
- 구조체 통째 전송 거부: 패딩·바이트 순서에 기대 "지금 이 기계에선 된다"로 통과하고 나중에 깨짐
- 빅엔디언: 느리지만 덤프를 눈으로 읽음(100이 `00 00 00 64`). 이 계층 디버깅 대부분이 16진수 필드 세기
- 체크섬 없음: TCP가 한다, 두 겹이면 한쪽만 고치는 일. (저널은 반대로 CRC — D-33)
- 길이 선행: 구분자는 이스케이프로 길이가 변함, 부분 수신 처리도 단순
- 상한 없으면 `body_len=0xFFFFFFFF` 하나로 4GB 할당
- magic 오류(`ERR_INVALID_ARG`)와 판 불일치(`ERR_NOT_SUPPORTED`)를 구분
- 테스트는 왕복이 아니라 **손으로 적은 기대 바이트열 24개**(인코딩·디코딩이 같이 틀려도 통과하는 걸 막음)

**D-26. 전문 종별 — 코드 0 미사용, 채움 바이트 없음, 디코딩은 길이가 정확히 같을 때만, 인코딩은 자리가 모자라면 한 바이트도 안 씀** (T3-02)
- 긴 전문을 허용해 앞만 읽으면 필드 재배치된 판에서 조용히 틀린다

**D-27. 리스너 — 포트 0 허용, `SO_REUSEADDR` 켬, `SO_REUSEPORT` 안 씀, `SA_RESTART` 끔, 모르는 종별은 끊음** (T3-03)
- **결정성의 경계를 여기서 긋는다**: 네트워크는 결정적일 수 없으니 소켓·시그널을 이 파일에 가두고 처리 훅은 바이트와 헤더만 받는다
- `SA_RESTART`를 켜면 `accept()`가 자동 재시작돼 멈춤 플래그를 볼 기회가 없다

**D-28. 워커 풀 — 공유 리스닝 소켓에서 각자 `accept()`** (T3-04)
- 선택지: (a) 부모 accept + `SCM_RIGHTS` / (b) 공유 리스닝 소켓 / (c) `SO_REUSEPORT`
- 고른 것: (b)
- 이유: (a)는 부모가 모든 접속의 길목(없애려던 병목이 돌아옴). (c)는 연결이 특정 워커에 묶여 그 워커가 죽으면 큐의 접속도 사라지고 편중 관측 불가. thundering herd는 `accept()` 직접 대기에선 리눅스가 하나만 깨워 문제 아님(herd는 epoll로 리스닝 fd를 볼 때)
- 건수 보고는 파이프 1바이트(원자적, 락 없음). 이후 T6-03에서 매칭 엔진이 들어오며 이 경로는 쓰지 않게 됨

**D-29. 공유메모리 — 익명 `mmap(MAP_SHARED|MAP_ANONYMOUS)`, fork 전 초기화, 오프셋만 저장, 캐시라인 64B 정렬** (T3-05)
- 선택지: (a) System V `shmget` — 재부팅까지 살아남아 `ipcs`로 수동 정리 / (b) POSIX `shm_open` — 이름 충돌·`/dev/shm` 찌꺼기 / (c) 익명 mmap
- 이유: 함께 쓰는 게 fork한 자손뿐. **경합을 코드로 막지 않고 설계로 없앴다**(초기화가 fork 전). 포인터 대신 오프셋은 매핑 방식이 바뀌어도 안 깨짐. 64B 정렬은 거짓 공유 방지
- 테스트: `MAP_PRIVATE`로도 mmap은 성공하므로 **fork 뒤에 쓴 값**을 양방향 확인, 순서는 sleep 대신 파이프

**D-30. 계좌 — 계좌 단위 robust 뮤텍스, 죽은 주인이면 되돌리고 `pthread_mutex_consistent()`** (T3-06)
- 선택지: 원장 전체 락 / 계좌 단위 락
- 이유: 전체 락이면 다른 계좌끼리도 줄을 선다(대가 1만 계좌 × 40B = 400KB). 죽은 워커의 락은 자리를 채워도 안 풀린다 → `PTHREAD_MUTEX_ROBUST`. `EOWNERDEAD`는 데이터 온전성 보장이 없다는 뜻 → `mutating` 표시 + 직전 값으로 **되돌린다**(굳히면 "증거금은 묶였는데 주문은 없는 계좌"). consistent를 안 부르면 영구 `ENOTRECOVERABLE`
- 불변조건 `0 <= reserved <= cash`를 `apply()` 한 곳에서

**D-31. 주문 검증 순서 — 계좌 → 종목 → 유형 → 수량 → 가격·호가단위 → 한도 → 증거금(마지막만 락)** (T3-07)
- 이유: 형식이 틀린 주문이 계좌 락을 쥐지 않게. **거부 사유를 정확히 말하기 위해서도** — 증거금부터 보면 호가 단위 오류가 "증거금 부족"으로 거부된다
- 확인과 묶기를 `acct_reserve()` 하나로(TOCTOU 방지), 증거금 올림(1,000,001원 40%에서 1원 덜 묶임 방지)
- 포기: **시장가·중간가를 원장에서 받지 않음**(체결돼야 가격을 앎, 참조 가격 관리가 또 하나의 주제), 매도 보유 수량 확인은 범위 밖

**D-32. FEP 이벤트 루프 — 레벨 트리거, 논블로킹 강제, 묶음 처리 중 등록 재확인** (T3-08)
- 선택지: 에지 트리거 / 레벨 트리거
- 이유: ET의 이점은 fd 수만 개일 때. FEP는 거래소 접속 몇 개. 잃는 것은 "EAGAIN까지 덜 읽으면 조용히 멈춘다"는 버그 종류. **빠른 것보다 틀리기 어려운 것.** 블로킹 fd는 등록 자체를 거절. 앞선 콜백이 fd를 닫으면 번호가 재사용돼 엉뚱한 접속 콜백이 될 수 있어 매번 재확인

**D-33. 전문 조립 — 어긋나면 재동기하지 않고 끊는다** (T3-09)
- 선택지: magic을 훑어 재동기 / 접속 끊기
- 이유: 재동기는 바이트 유실 가능한 전송(직렬, UDP)의 기법. TCP에서 어긋났다면 우리 조립 상태가 틀린 것이고, 훑으면 0x4D53이 가격·계좌번호 안에서 금방 나와 **그럴듯한 거짓 전문**이 생긴다. 끊으면 T3-11 재접속이 처음부터 맞춘다
- 한도 초과는 바디를 기다리기 전에 거절, body 포인터는 다음 호출까지만 유효(전문마다 할당 안 함)

**D-34. 송신 큐 — 가득 차면 버리지 않고 호출부에 알림, 전문을 반만 넣지 않음, `EV_WRITE`는 보낼 게 있을 때만, EAGAIN/EPIPE 구분** (T3-10)
- 이유: 조용히 버린 주문은 "보냈는데 응답 없는 주문"과 구분 안 됨 — T3-14의 가장 어려운 문제를 스스로 만든다. LT에서 EPOLLOUT을 켜 두면 루프가 쉬지 않고 깬다. EINTR은 EAGAIN 쪽

**D-35. 세션 — 시각을 읽지 않고 `now_ms`를 받음, 소켓은 호출부가 만듦, "보낸 지"와 "받은 지"를 따로, 로그인 전 업무 전문 금지, 백오프 리셋은 로그인 시점, 지터 없음, 하트비트 되받아치지 않음** (T3-11)
- 이유: **경계가 읽고 논리는 받는다** → 테스트에 sleep 0, 같은 입력에 같은 상태 변화("가끔 실패하는 테스트"는 버그를 숨기는 가장 좋은 방법). 하트비트는 내가 살아 있음(보낸 지 기준), 무응답 단절은 상대 생존(받은 지 기준). 지터는 많은 클라이언트의 동시 재접속을 막는 장치인데 거래소마다 접속 하나, 넣으면 시드 주입 난수가 필요

**D-36. 시퀀스 복구 — 갭 뒤는 보류하지 않고 버린 뒤 "빠진 번호부터 전부 다시"(`RESEND_REQ`), 없는 구간은 `GAP_FILL`, 번호는 모든 전문을 세되 막는 건 업무 전문만** (T3-12)
- 선택지: 재정렬 버퍼 / 버리고 재요청
- 이유: 재정렬 버퍼는 크기·미충족 처리를 또 정해야 하고 틀리면 **조용히 순서가 뒤바뀐 채** 올라감. 대가는 이미 본 전문을 한 번 더 받는 것(재접속 때만, 싸다) — 대신 중복을 반드시 버려야 성립. 재전송 요청을 로그인에 실으면 `LOGIN_REQ` 길이가 바뀌어 호환이 깨지고 갭은 재접속 때만 생기는 것도 아님. 세션 전문까지 갭에 막으면 **갭에서 빠져나오는 열쇠를 갭 안에 가두는 셈**

**D-37. 거래소 주문번호 매핑 — 선형 탐색, 응답 전 취소는 우리 번호(`order_id=0`)로, 가득 차면 끝난 주문부터 밀어냄, 끝난 주문을 곧바로 지우지 않음, 같은 번호 재등록 거절, 수량 집계 안 함** (T3-13)
- 응답 전 취소 선택지: 거절(사용자에게 떠넘김) / 보류(취소 지연 = 돈, 세션 끊기면 T3-14 문제 추가) / **우리 번호로 전송** ← `CANCEL_REQ`가 두 번호를 모두 싣도록 설계돼 있어 거래소가 받았으면 취소, 못 받았으면 "없는 주문"으로 깔끔히 거부
- 선형 탐색은 재 본 적 없어서 최적화를 미룸(한계를 헤더에)
- 수량 집계는 T2-09의 일 — 두 군데서 세면 언젠가 어긋나고 어느 쪽이 맞는지 모른다

**D-38. 미응답 주문 — `IN_DOUBT`로 판정 보류, 자동 재전송 안 함, 재접속 후 당일 전체 조회로 판정** (T3-14, T4-04)
- 이유: 끊긴 순간 응답 못 받은 주문은 (1) 못 받음 (2) 받고 접수 (3) 받고 거부. 우리 정보로 1과 2를 못 가른다. "응답 없으니 거부"가 가장 흔하고 가장 위험(모르는 포지션). 재전송은 2번이면 **같은 주문이 둘** — 이 계층의 가장 비싼 실수
- 채널계에서도 **202 + `IN_DOUBT`**, 자동 재시도 없음. 200은 없는 주문을 있다고, 5xx는 있는 주문을 없다고 말하는 것
- 조회가 또 끊기면 보류 유지, 보류도 "끝나지 않은 주문"으로 셈

**D-61. 원장 취소 — 푸는 금액은 "취소된 수량 × 지정가", 남의 주문은 "없다"로** (T7-01)
- 이유: 묶음 = 지정가 × 살아 있는 수량이라는 불변식(T6-03)이 그대로 이어진다. 일부 체결 뒤 취소도 같은 식으로 맞는다(체결분은 콜백이 이미 풀었다) — 20주 중 12주 체결 뒤 취소하면 8주분만 풀린다
- "권한 없음"으로 구별해 답하면 주문번호를 넣어 보며 남의 주문 존재를 알아낼 수 있다 → 소유 검사를 통과하지 못하면 없는 주문과 같은 `ERR_NOT_FOUND`
- 포기/한계: 한쪽 다리만 취소되고 다른 쪽이 실패하는 경로는 한 프로세스 안에서 만들 수 없어 시험하지 못함(주석). 정정은 여전히 `ERR_NOT_SUPPORTED`
- 검증: 변이 10/10(기준 통과 먼저 확인). 위쪽 범위 검사 삭제는 배열 밖 읽기라 ASan 빌드에서 잡힘

**D-62. 주문 상세·잔고 전문 — 다리 목록 대신 시장 번호를 첨자로 쓰는 배열, 다리 체결 금액은 i64** (T7-02)
- 선택지: 다리 목록(가변 길이) / 시장별로 더한 고정 배열
- 이유: 한 시장에 다리가 여럿일 수 있어(PLAN_LEGS_MAX) 가변 목록이면 전문 길이가 흔들린다. 화면이 알고 싶은 것도 "어느 시장에 얼마". `MSG_LEG_SLOTS`(2)는 `_Static_assert`로 시장 수와 묶음. DETAIL_REQ 20B / DETAIL_ACK 91B / BALANCE_REQ 12B / BALANCE_ACK 32B(종별 17~20)
- i64: 70,000원 × 100,000주면 i32를 넘는다. 채널계가 나중 체결의 가격을 "금액 차이 / 수량 차이"로 정확히 내려면 반올림된 평균가가 아니라 금액이 필요(T6-07과 같은 이유)
- 채널계 코덱은 `WireField.count`에 `long[]`을 더함(D-53의 `int[]` 배열과 같은 방식)

### 5.4 내구성·검증 모듈

**D-39. 저널 — 입력만 기록, CRC(머리+바디), 찢어진 꼬리는 버림, 매 레코드 fsync** (T5-01, T5-05) — 3.5 참조
- 포기: 376 TPS. 그룹 커밋·전용 스레드·빠른 장치는 재 본 뒤 고른다

**D-40. 스냅샷 — 저널을 대신하지 않음, `upto_seq` 필수, 같은 디렉터리 임시 파일 + fsync + rename** (T5-02) — 3.5 참조

**D-41. 대사 — 대상 코드를 호출하지 않고 숫자만 받아 재계산, 첫 어긋남에서 멈추지 않음, "어디의 무엇이 얼마만큼"** (T5-03)
- 이유: 같은 버그를 두 번 쓰는 것은 검사가 아니다. 부수 효과로 `core`가 서로 못 보는 형제 `sor`·`ledger`를 링크하지 않아도 됨 — **의존성 제약과 설계 원칙이 같은 답**. 대사는 하루 한 번이라 첫 건에서 멈추면 나머지가 하루 뒤에 보임. 자리가 모자라도 끝까지 세어 `dropped`에("못 본 것은 없는 것이 아니다")
- 포기: 호출부가 `logical_order_t`를 `recon_order_t`로 옮겨 적는 수고

**D-42. 시세 피드 — 주문 전문과 다른 채널(magic `"MF"`), 증분 없이 매번 스냅샷, 갭이면 `stale` → 새 주문 금지·취소는 허용** (T5-06)
- 선택지: 증분 / 스냅샷
- 이유: 시세는 한 방향·요청 없음·다수 수신 → 재전송 요청 상대가 없다. 증분은 앞의 것을 모두 받았다는 전제에서만 뜻이 있고, 놓치면 잔량 200이 **오류가 아니라 틀린 값**으로 보여 전략이 믿고 주문. 스냅샷은 자기 완결적이라 다음 것으로 맞음
- 포기: 크기(10단에 200바이트대) — **재기 전에 아끼지 않는다**
- 형식은 `core`, 생성기는 `exchange` → "전략 엔진이 호가창 내부를 알 필요 없다"가 의존 방향만으로 지켜짐

**D-43. 주문 SDK — `core`만 의존, 최상위 `sdk/`, 주문번호는 SDK가 발급하되 첫 번호는 호출자가, 모르는 번호는 `orphans`로 셈, 정정은 응답 뒤 반영, 체결 수량은 큰 쪽** (T5-07)
- 이유: 내부를 링크하면 바깥 전략 엔진이 시뮬레이터를 통째로 끌고 감. 전략이 번호를 매기면 겹침을 응답 뒤에야 앎. 1부터 고정이면 재기동 = 번호 충돌. 조용히 버리면 체결이 사라진 걸 모름. 취소 실패를 주문 실패로 읽으면 없는 잔량을 잃음

**D-44. key=value 파서 공통화 — "세 번째 쓰임" 조건 전에 착수, 해석기 + 필드 주소 표** (T2-04 → T2-XX)
- 원래 미룬 이유: 두 곳의 요구가 갈리는지 모르는 채 인터페이스를 굳힘. 사용자가 지금 하기로 정함 — T1-18부터 Phase 5까지 한 줄도 안 갈라져 "기다린 시간이 답했다"
- 키마다 핸들러면 한 줄짜리 함수 13개 → 필드 주소를 표에

### 5.5 채널계·화면·통합

**D-45. 채널계 빌드는 Windows, C는 WSL** (T1-01, B-01, T4-01)
- 이유: WSL이 필요한 이유는 C의 ASan/UBSan 하나. Java 17(설치돼 있고 Boot 4.x 하한), 시스템 Maven 대신 `mvnw`

- 포기/한계: 길이 합이 같고 순서만 다른 배치는 못 잡음 — 적어 둔 한계 → T6-01에서 열거값 값 대조를 더함

**D-48. 원장 커넥션 풀 — 블로킹, 비면 기다렸다 실패(늘리지 않음), 깨진 접속은 버림, 타임아웃 난 접속도 버림, 밀려오는 전문은 이 풀이 다루지 않음, 시퀀스는 접속마다** (T4-03)
- 이유: 채널계는 요청-응답이라 이벤트 루프가 벌 게 없고 동시성은 접속 수로. 무한정 늘리면 원장이 **전부 함께 느려짐**. 답을 못 받은 접속을 계속 쓰면 **응답이 한 칸씩 밀려** 다음 요청이 앞 요청의 답을 받는다(값이 그럴듯해 한참 뒤 드러남). 체결 통보가 섞이면 주문 응답 자리에 남의 체결이 옴
- 테스트: 64건 × 8스레드로 각자 제 답을 받는지

**D-49. 풀 크기 1** (T6-03)
- 이유: 원장이 단일 프로세스·단일 접속 리스너(호가창을 하나로 유지). 8이면 동시 주문이 5초 매달림
- 포기: 채널계→원장 동시성
- 뒤따른 일: 크기 1이 되자 옛 풀의 경합이 "갇힌 주문"으로 값이 바뀌어 T6-11에서 세마포어로 고침(D-59)

**D-50. REST 상태 코드 — 400(형식) / 422(원장 거절) / 503(못 붙음) / 202(응답 없음)** (T4-04)
- 이유: 전부 500이면 "고쳐서 다시"와 "기다렸다 다시"를 못 정함. 못 붙었으면 주문이 확실히 안 나갔으므로 모호하지 않다(503). 보낸 뒤 답이 없어야 모호(202)
- 테스트: 형식 오류가 원장까지 안 가는 것을 요청 수로, 답을 못 받은 뒤 다음 주문이 멀쩡히 나가는 것으로 깨진 접속 폐기 확인

**D-51. WebSocket — 요청-응답 풀과 분리, 느린 구독자는 빼고 끊음, `ledger-down` 사건** (T4-05)

**D-53. BOOK_ACK — 가격·수량을 단마다 섞지 않고 배열 넷으로** (T6-04)

**D-54. CORS를 채널계에 여는 대신 Vite 프록시** (T6-05)

**D-55. 화면 — 어두운 배경, 매수 빨강/매도 파랑(국내 관행), `tabular-nums`, 응답 세 갈래(접수/거절/확인 필요), SOR 패널에 항목별 차이, 전략 비교 막대는 체결률** (T4-06~T4-13)

**D-60. 원장 상태 알림 — 바뀔 때만 방송, 새 구독자에게는 현재 상태** (T6-10) — 3.6 참조
- 이유: 1초 호가 읽기마다 실패 알림이 쌓이지 않게. 방송만 하면 늦게 온 화면이 모른다
- 포기: 풀이 2초 넘게 비지 않으면 원장이 살아 있어도 "끊김"으로 보일 수 있다

**D-63. 취소 응답 — 원장의 같은 `ERR_NOT_FOUND`를 409와 404로 나눈다** (T7-03)
- 이유: 원장은 "이미 끝남"과 "없음·남의 주문"을 같은 코드로 답한다(D-61). 채널계가 낸 주문이면 "이미 끝남"(409), 모르면 404 → 화면이 "다시 누를 필요 없음"과 "번호가 틀림"을 구별해 보여 줌
- 취소의 503은 주문의 503과 달리 다시 보내도 안전 — 두 번째는 "잔량 없음"일 뿐

**D-64. 원장 상태 밀어 보내기 — 구독 접속 대신 주기적으로 다시 읽어 바뀐 것만 방송(`LedgerPoller`)** (T7-03)
- 이유: 원장은 요청-응답만. 구독 접속을 새로 만들지 않고 T4-05의 완료 조건("체결 통보·호가 갱신을 화면에 밀어 보낸다")을 지킴. 1초 간격, record `equals`로 비교
- **끝난 주문은 다시 묻지 않는다**: 목록이 500건이면 매초 500번 원장을 부르고, 접속 풀은 1개다
- **나중 체결 가격은 "금액 차이 / 수량 차이"**: 평균가 차이로는 두 번째 체결 가격이 나오지 않는다(시험: 70,000에 4주 뒤 69,900에 2주 → 두 번째 방송 가격 69,900)
- 포기: 약 1초 지연, 원장 접속 1개를 주문과 나눠 씀(원장 처리는 마이크로초라 주문을 눈에 띄게 늦추지 않음 — ponytail 주석). 주문 목록은 채널계 메모리(500건)
- 검증: 변이 16개 — 처음 12 잡힘, 3 생존(M7·M13·M16 → 4.8), 1 판정 불가(M11)

**D-65. 접수 직후 체결을 시장별로 나눠 방송** (T7-03)
- 이유: 접수 응답에는 시장이 없다. SOR 주문의 체결을 "고른 시장(255)"으로 보내면 화면은 어디서 체결됐는지 모른다 → 접수 뒤 상세를 한 번 읽어 다리마다 방송
- 포기: 상세를 못 읽으면 예전처럼 한 줄(고른 시장 값)

**D-66. 화면의 원장 상태 — 처음에 한 번 읽고 방송으로 고침, 1초 호가 끌어오기 제거** (T7-04)
- 이유: 채널계가 바뀐 호가만 밀어 보냄(D-64). 끌어오기는 방송이 끊겼을 때 3초마다, 붙어 있어도 20초마다 전체를 다시 맞추는 대비로만
- 포기: 체결 내역은 화면 메모리라 새로고침하면 사라짐(T7-04 "남은 것")

**D-67. 예상 체결은 화면에서 계산한다** (T7-05)
- 선택지: 원장에 "해 보기" 전문 추가 / 화면이 보이는 호가로 계산
- 이유: 원장에 묻으면 정확하지만 주문창 입력마다 원장을 부른다. 보이는 10단 기준 참고값이라고 화면에 적고, 실제 배분은 바로 아래에 원장 값(최근 SOR 주문의 다리)으로 보인다
- 검증: 웹에는 시험 도구가 없어 `npm run check`(Node 타입 제거 실행)로 예상 체결 4경우·호가 단위 9경우

**D-68. 거래 한 화면, 주문 결과 알림과 체결 알림 분리, 입력칸 Enter로는 주문하지 않음** (T7-05)
- 탭 넷(거래·주문체결·전략·관제)을 거래 한 화면으로: 호가·시장 비교·미체결/체결·주문창·잔고를 함께 본다
- **알림 분리**: 접수 즉시 체결은 방송으로도 오므로 둘 다 띄우면 한 체결에 알림이 둘. 방송이 붙어 있으면 체결 알림은 방송 쪽만, 끊겼으면 주문 응답으로
- **Enter만으로는 주문하지 않는다**: 수량을 고치다 Enter를 치는 실수가 곧 주문이 되면 안 된다. 주문은 버튼이나 Ctrl+Enter. B/S는 `e.code`라 한글 입력 상태에서도 된다
- 접근성: 매수/매도·상태·시장은 늘 글자 태그와 함께(색만으로 뜻을 전하지 않음), 호가 줄마다 읽을 이름, `prefers-reduced-motion`이면 애니메이션 없음. 좁은 화면 1180/760/520px 단계

### 5.6 변이 검사 분류와 처분 규칙 (방법론 판단)

**D-58. "대신 막아 주는 쪽이 우리 코드면 지운다, 커널·규격의 사정이면 남긴다"** (인수인계, T3-08~T3-12)

- 중복을 지울 때 중복이 막아 주던 것을 잃지 않게: T3-13 `add`를 구조체 한 번 대입으로 바꿔 필드가 늘어도 자동 0
- 반례도 있다: T5-01 J3는 "겹치니 남긴다", T5-06 D3는 "겹쳐 보일 뿐 막는 입력이 다르다" → **겹침을 발견하면 무엇을 막는지 끝까지 따진다**

## 6. 테스트·검증 방법론

### 6.1 세 빌드 게이트: Debug · Release · ASan

- **규칙**: 커밋 전 전체 테스트를 Debug, Release, ASan에서 돌린다(CLAUDE.md 세션 종료 절차). 최종 C 58/58 × 3(T6-08, Phase 7의 T7-01·02·07에서도 58/58 × 3)
- **Release가 따로 필요한 이유 (실제로 잡힌 것)**
  - assert 기반 테스트가 `NDEBUG`로 사라져 **아무것도 검증하지 않고 통과**(T1-20) → 테스트 타깃 `-UNDEBUG`
  - `(void)read`가 `-O2 + _FORTIFY_SOURCE`의 `warn_unused_result`에 걸림(T3-03)
  - `-Wstringop-truncation`은 `-O2`에서만 컴파일러가 증명(T3-11 인수인계, T5-03 재발)
- **ASan이 따로 필요한 이유**
  - T6-03 L13 용량 검사 삭제가 Debug에선 통과, ASan에서 heap-buffer-overflow
  - ASan이 실제로 동작하는지부터 확인했다: `ldd`에 libasan.so.8, 의도적 범위 밖 접근이 잡히는지(T1-01)
  - 한계도 안다: libc 내부(`fread`)가 넘쳐 쓰는 것은 ASan이 못 가로챈다(T5-01 J3)
- **컴파일 옵션**: `-std=c11 -Wall -Wextra -Werror -Wshadow -Wconversion`. 경고는 곧 빌드 실패
- Java는 `mvnw test`(Windows, Phase 8 이후 69개), 화면은 `tsc -b && vite build`, `oxlint`, `npm run check`(T7-05)

### 6.2 변이 검사

**방법**: 생산 코드를 한 곳 망가뜨려 빌드·테스트. 태스크마다 변이 수와 잡힌 수를 기록했다(예: T3-12 22/22, T5-03 18/18, T6-03 19/20).

**"잡히지 않음"의 다섯 가지 뜻과 처분** (T3-05·06·10·14, T5-01, 인수인계)
| 종류 | 예 | 처분 |
|---|---|---|
| 1. 진짜 테스트 구멍 | T3-05 정렬 검사, T5-02 S4 magic, T5-07 K16, T5-06 D3 | 테스트 추가 |
| 2. 도달 불가능한 방어 | T3-05 곱하기 전 넘침(타입 범위상 발화 불가), T5-02 S11 | 남기고 이유 기록 |
| 3. 규격은 요구하나 이 구현에서 구분 안 됨 | T3-06 `PTHREAD_PROCESS_SHARED`, T3-10 S9 | **절대 빼지 않음** |
| 4. 아무 일도 하지 않는 대입 | T3-14 D3, T5-02 S10 | `assert`로 바꿈 — 검증이 아니라 **앞으로를 위한 덫**(성립하는 단언은 변이로 확인 불가) |
| 5. 확인할 수 없는데 지우면 안 되는 것 | T5-01 J3 | 한도를 버퍼 크기에서 끌어와 관계를 드러냄 |

그 밖에 **원리상 못 잡는 것**: T1-07 항등 해시(정확하고 느릴 뿐 — 벤치의 몫), T3-07 TOCTOU(확률 의존 — 원자성은 T3-06이 지킴), T5-04 fsync(SIGKILL로 전원 유실 불가).

**변이 검사의 실패 모드** → 3.3 표. 요약하면:
1. 원본이 먼저 통과하는지 확인 (T6-04)
2. 빌드 실패는 잡힘이 아니다 — 값 바꾸는 변이로 (T1-09, T5-02, T5-05, T6-01)
3. 치환이 적용됐는지 `cmp -s`, 의도한 자리인지 눈으로 (T5-03, T3-11)
4. CRLF, `/mnt/c` 시계, 남은 목적 파일, SIGKILL로 복구 안 된 변이 (`486595f`, 인수인계)

**변이가 가르친 테스트 설계 원칙**
- **경계값은 맞아떨어지지 않는 값으로**: T3-11 max=1600(=100×2⁴) → 1000, T1-06 기준가 7,778
- **테스트 데이터가 편하면 두 규칙이 같은 답을 낸다**: T2-07 나머지 규칙, T3-13 O3 색인 순서
- **거부가 버그를 가린다**: T1-09 price=0이 제한폭에 막힘
- **두 검사가 같은 입력에 걸리면 서로를 가린다** → 거절 이유까지 대조(T3-03), 한쪽만 발화하는 입력(T3-05 크기 −1, T1-11 가격 변경 경로)
- **증상이 나타날 수 있는 조건을 만들어라**: T1-17 기준가 4,990 · 도착률 10억/초, T3-10 소켓 버퍼 4KB
- **"깨진 입력"과 "남의 입력"은 다르다**(T5-02 S4)
- **변이가 코드의 자리를 고치기도 한다**(T3-12 R6 → `session_drop`)
- 변이를 테스트가 아니라 **테스트가 지킨다고 주장하는 생산 코드에 건다**(T5-04)
- **가짜 상대역도 검증 대상이다**: 가짜 원장이 진짜와 다르게 답하면 시험이 코드의 실수를 가려 준다(T7-03 M7)
- **결과가 같고 비용만 다른 변이는 결과만 보는 시험으로 못 잡는다** → 호출 수를 센다(T7-03 M16)
- **테스트를 먼저 실패시킬 수 없으면 변이로 대신한다**: 새 종별은 없으면 컴파일부터 안 된다(T7-02)

### 6.3 결정성 검증

- 규약: 엔진은 시스템 시각을 읽지 않고(논리 시각), 난수는 시드 주입, 해시 순회 의존 금지, 단일 스레드(CLAUDE.md)
- **T1-19**: 파이프라인 전체(유동성 생성 → 두 시장 엔진 → 이벤트)를 두 번 돌려 **이벤트 하나하나를 바이트 비교**. 시장당 5만 건, 이벤트 218,064건, 체결 9,804,799주, 체결금액 99,025,878,600원. 요약 해시가 아니라 바이트 — 어긋난 지점을 찾고 충돌 가능성 제거. 두 번째 실행은 들어오는 자리에서 대조(배열 두 벌 불필요)
  - 반대 방향도 검증: 시드가 다르면 달라지고 시나리오가 다르면 체결량이 달라져야 한다 — 안 그러면 "아무것도 안 하는 코드"도 통과
  - `assert(elapsed < 25.0)`(CI 30초 조건을 못 박음)
  - **첫 실행에서 구조체 패딩 비결정성 발견** → `memset`
- **T2-12**: 같은 프로세스에서 두 번 돌리면 스택이 같아 패딩이 우연히 일치 → **스택을 0xAA로 덮어** 우연 제거
- **T1-12**: 이벤트 순서를 헤더에 못 박음(REJECTED 하나 / maker 먼저 taker 다음 / ACCEPTED / CANCELED) — 순서를 문서화하지 않으면 "결정적"이 검증 대상이 아니라 구현 산출물이 된다. `match_cancel`/`match_modify`에 `ts` 인자 추가
- **T2-14, T5-08**: 같은 시드로 두 번 돌려 리포트가 **바이트까지 같다**. 날짜를 인자로 받는다

### 6.4 장애 주입과 실제 조건 만들기

"흉내는 내가 상상한 모양만 만든다"(T5-04)는 원칙으로, 가짜 대신 실제 조건을 만든 사례:
- **실제 SIGKILL** — 저널·스냅샷(T5-04), 워커 풀 강제 종료(T3-04)
- **락 쥔 채 진짜로 죽이기** — 자식이 잠그고 `mutating`을 세우고 값을 망가뜨린 뒤 `_exit`, 부모가 `EOWNERDEAD`로 되돌림. robust가 꺼져 있으면 실패가 아니라 **멈춤**으로 나타남. "쓰기 중이 아닐 때 죽은 경우"도 따로 — 회수가 곧 되돌리기는 아니다(T3-06)
- **진짜 소켓** — 가짜 fd로는 bind·accept·부분 수신·EINTR이 빠진다. 한 바이트씩 보내 부분 수신 강제(T3-03), 1바이트씩 흘려 넣어 마지막 바이트가 들어온 **바로 그때** 전문이 나오는지(T3-09)
- **진짜 TIME_WAIT** — 서버가 먼저 끊게(T3-03)
- **진짜 부분 쓰기** — 소켓 버퍼 4KB + 200KB, `rounds > 1`(T3-10)
- **반닫힘** — `shutdown(SHUT_WR)`(T3-08)
- **진짜 두 프로세스 + 진짜 매칭 엔진** — 상대역이 응답을 지어내면 통합이 아니라 각본. 70,100에 60주 → 30@70,000 + 30@70,100(T3-15). 기다림은 `poll` + 횟수 상한, 매달리면 실패
- **진짜 거래소 거부** — "한쪽 거부"를 흉내 내지 않고 18:00(NXT 단독)에 양 시장 계획을 보내 KRX가 실제로 거절(T2-10)
- **진짜 브라우저** — Chrome DevTools로 주문 → 체결 → 호가 변화 확인(T6-05). 자바 테스트는 CORS를 못 잡는다
- **진짜 원장 장애** — 화면을 띄운 채 `ledgerd`를 죽였다 살려 "원장 끊김" 표시와 자동 회복, 회복 직후 주문 체결까지 확인(T6-10·11, T7-05에서 다시)
- **사람처럼 눌러 보기** — T7-04에서 잔고 부족 거절, SOR 매도·매수, 걸어 두기 → 나중 체결 → 취소, 새로고침 뒤 목록 유지, IOC 40,000주 중 35,679주 체결, FOK 거절을 브라우저로 확인. 이 확인에서 1원 차이(T7-07, 3.7)를 찾았다. T7-05는 1440·1024·500px에서 가로 스크롤 없음까지
- **간헐 실패는 횟수를 센다** — SIGTERM 경쟁을 6회 중 2회로 확인, 회귀 테스트 60회(`80fe53e`). "왜 고쳐졌는지 설명할 수 없으면 아직 고친 것이 아니다"
- **테스트는 줄 수 없는 보장을 요구하지 않는다** — SIGKILL 워커 기대값 7~8(T3-04)

## 7. 한계와 다음 단계

문서에 적힌 것만 옮긴다.

### 7.1 동작 범위의 한계
- **SOR·매칭 엔진은 원장 프로세스 안**에서 돈다. FEP를 사이에 둔 다중 프로세스 구성은 T3-15 통합 테스트로만 검증했다(CLAUDE.md, T6-03). 아키텍처 그림의 "각 계층은 별도 프로세스"는 실행 구성과 다르다
- 원장은 단일 프로세스·단일 스레드, 채널계 풀 1(T6-03)
- **취소는 된다**(T7-01, T7-03). **정정은 연결하지 않아 여전히 `ERR_NOT_SUPPORTED`**(T6-03)이고 채널계·화면에 정정 API·버튼이 없다
- 나중 체결·호가·잔고 변화는 채널계가 **1초마다 원장을 다시 읽어** 밀어 보낸다(T7-03) — 약 1초 늦고, 원장 접속 1개를 주문과 나눠 쓴다
- **주문 목록은 채널계 메모리(500건)**다. 채널계를 다시 띄우면 비고, 원장을 다시 띄우면 원장 쪽 주문이 사라진다(T7-03 ponytail 주석)
- **체결 내역은 브라우저 세션 메모리**다 — 화면을 연 뒤 방송으로 온 체결만, 새로고침하면 사라진다(T7-04 "남은 것")
- **예상 체결은 보이는 10단 기준 참고값**이다. 더 깊이 쓸어 담는 주문은 적게 잡히고, 실제 배분은 원장이 정한다(T7-05)
- 채널계에 주문 상세 API는 생겼지만(T7-03), `IN_DOUBT` 주문은 원장 주문번호를 몰라 **"조회로 확인"할 수 없다**. cl_ord_id 조회가 먼저 필요(T6-06, T7-03 주석)
- 원장 검증은 **시장가·중간가를 받지 않는다**, 매도 보유 수량 확인은 범위 밖(T3-07)
- `acct_open()`은 계좌 단위 락으로 보호되지 않아 fork 전에 계좌를 다 여는 것이 전제(인수인계)
- **실시세 모드는 시장 충격을 재현하지 않는다**(Phase 8). 내 주문이 바깥 호가를 소모하지 않으므로 시세는 내가 무엇을 하든 그대로 흘러간다. 큐 우선순위는 재현한다(내 앞 잔량이 먼저 빠져야 내 차례가 온다) — 호가 한 단을 흔들지 못할 만큼 **작은 주문**에서만 받아들일 만한 근사다
- **실시세는 시장이 하나다**(T8-04). 토스 Open API의 국내 호가는 통합(KRX+NXT)만 주고 `GET /api/v1/orderbook`의 파라미터가 `symbol` 하나뿐이다. 그래서 두 시장·SOR 배분·전략 비교는 시뮬 모드에서만 볼 수 있다
- **토스 토큰은 client 당 하나**다. 재발급하면 이전 토큰이 즉시 무효가 되므로 같은 키로 프로세스를 둘 띄우면 서로 죽인다. 허용 IP를 등록하기 전에는 403(`access_denied`, `IP address not allowed`)이었고, **등록 뒤 토큰 발급·구독·호가 수신까지 실제로 성공했다**(2026-09-19)
- **실호가를 심으려면 원장 기준가를 종목의 실제 가격에 맞춰야 한다**. 호가창은 기준가 ±30%(가격 제한폭)만 펼치므로 그 밖의 가격은 버려진다. 005930이 26만원일 때 기본값 70,000원으로 띄우면 스냅샷이 통째로 사라졌다. 처음에는 `ledgerd --ref-price <원>`을 손으로 줬는데, **그 상태의 화면은 사용자가 할 수 있는 일이 없다** — "서버를 다시 띄워라"라고 적혀 있을 뿐이다. T8-10에서 **가격대를 아는 쪽(채널계)이 고치게** 했다: 보낸 최우선 가격이 응답 호가창에 없으면 `SYMBOL_SET`으로 그 가격대의 호가창을 새로 연다(30초에 한 번까지)
- **종목을 바꾸는 방법은 호가창을 다시 만드는 것뿐이다**(T8-10). 가격 제한폭이 호가창을 만들 때 정해지기 때문이다. 그래서 종목 전환은 "원장을 새로 여는 일"이고 미체결 주문과 잔고가 초기화된다 — 한 종목짜리 원장에서 앞 종목의 주문을 다른 가격대의 호가창에 남겨 둘 자리가 없다. 숨기지 않고 화면에 적었다
- **채널계가 다시 뜨면 원장이 무엇을 들고 있는지 물어야 한다**(T8-10). 설정에 적힌 종목(005930)을 들고 시작하면, 그사이 종목이 바뀐 원장은 자기 종목에만 답하므로 **모든 호가 조회가 빈 호가창**이 된다. `SYMBOL_SET`의 기준가 0을 "묻기만 한다"로 정해 그 자리를 만들었다
- **토스에는 이름으로 종목을 찾는 API가 없다**(T8-10). 있는 것은 마켓별 전체 목록(`GET /api/v1/stocks/all`)뿐이라 KOSPI·KOSDAQ 보통주 목록을 받아 두고 이쪽에서 거른다. 하루에 한 번 바뀌는 값이라 6시간 캐시하고, 레이트리밋(429)은 `Retry-After`를 따라 두 번까지 다시 부른다 — 한 번 받아 두면 여섯 시간을 쓰는 목록이라 여기서 포기하면 사용자가 할 일이 "다시 누르기"밖에 없다
- **같은 키로 토큰 발급기를 둘 만들면 서로를 죽인다**(T8-10에서 찾음). client 당 유효한 토큰이 하나인데, 실시세 클라이언트와 차트 조회가 각자 `TossTokenSource`를 만들고 있었다. 한쪽이 발급하는 순간 다른 쪽 토큰이 무효가 된다. 스프링 빈 하나로 합쳤다 — 클래스 주석에 "여기서만 발급한다"고 적혀 있었는데 정작 둘이 있었다
- **테스트가 `.env`를 읽고 있었다**(T8-10에서 찾음). 본 설정이 `spring.config.import`로 루트 `.env`를 끌어오는데 테스트도 같은 설정을 쓴다. 키가 채워진 뒤로는 **테스트를 돌리는 것만으로 바깥에 접속하고, 새 토큰을 발급해 돌고 있던 실시세 세션을 죽였다.** 테스트용 `application.properties`로 끊었다
- **유휴 WebSocket은 서버가 끊는다.** 장이 닫혀 송수신이 없으면 2분 48초 만에 끊겼고 재연결도 한동안 거부됐다. 30초마다 표준 Ping 프레임을 보내고, 끊길 때 `abort()`로 연결을 놓아준다
- 화면의 거래량 막대는 **내 주문의 체결 수량**이다. 시장 전체 거래량이 아니다 — 원장이 체결을 내 주문에 대해서만 통보하기 때문이다(T8-05)

### 7.2 성능·내구성
- 매 레코드 fsync로 **376 TPS**. 바꿀 때 선택지: 그룹 커밋 / 저널 전용 스레드 / 더 빠른 장치 — 재고 고른다(T5-05)
- T5-05 수치에는 **전문 송수신·프로세스 경계 비용이 빠져 있다**(한 프로세스 안), 측정 자체 비용(`clock_gettime` 두 번) 포함, WSL2 ext4(VHDX on NVMe) 기준 — 다른 장비는 다시 재야 한다
- 장애 주입(SIGKILL)으로는 **fsync 유무와 CRC 필요성을 검증할 수 없다**(전원 유실 미시험)(T5-04)
- FEP 거래소 번호 매핑은 **선형 탐색**, 재 본 적 없음(T3-13)
- 해시 품질은 정확성 테스트로 못 잡는다(ADR-0001), 간접 호출 비용은 재검토 조건(ADR-0002)
- `listener.c`의 `write_exact` 블로킹 부분 쓰기 경로는 여전히 미시험(인수인계)

### 7.3 실험(측정)의 한계
- **매수만** 낸다 — CROSSED에서 밀린 시장이 유리해지는 국면은 표에 없다(T2-14)
- **세션 규칙을 걸지 않았다**(T2-14)
- **시드만 바꿨다** — 기준가·주문 크기·공격도 고정(quality 리포트)
- **정수 bp 해상도** — 0.5bp 미만 차이는 비김(T6-07)
- 수수료 KRX 3bp / NXT 2bp는 **가정값**(ADR-0005)
- 중간가는 단순화 — 실제와 다를 수 있음(ADR-0003), 스프레드 한 틱이면 가격 개선 없음
- SWEEP 훑기 깊이 64단(T2-08), 쪼갠 FOK는 다리 안에서만 전량 보장(T2-10)
- 세 양시장 전략은 **실제로 같은 호가를 다 먹어** 평균 단가 차이가 0.001bp 수준 — 차이는 주문별 슬리피지(0~2bp)에서만 보인다(T6-07)

### 7.3.1 실시세·리플레이의 검증 한계 (Phase 8)
- **붙었다**(2026-09-19, 허용 IP 등록 뒤). 토큰 발급 → WebSocket → 구독 수락 → REST 호가 수신까지 확인했다. 장중 스냅샷 흐름과 체결 메시지의 실제 모양은 아직 못 봤다
- **체결 토픽은 실험으로 확정했다**: `realtime-trade:kr`은 `invalid-type`, **`trade:kr`은 수락**. 구독 응답이 `subscribed`/`rejected`를 돌려주므로 후보를 같이 보내 갈랐다
- (2026-09-18) 그전에는 토큰 발급이 토스가 `403 {"error":"access_denied","error_description":"IP address not allowed"}`로 답했다 — 키와 요청 형식은 맞고 **허용 IP 등록만 남았다**. 그 뒤(구독·수신)는 확인하지 못했다
- 429·403·gzip은 같은 규약으로 답하는 작은 HTTP 서버로, 스냅샷 경로는 가짜 피드로 시험했다. 장 시간과 허용 IP에 기대는 시험은 재현되지 않아 자동 테스트로 두지 않았다
- WebSocket 구독 선언(`[{"type":"orderbook:kr","codes":[...]}]`)과 수신 모양은 공개 `asyncapi.json`에서 읽은 것이고, 실제 메시지로 확인하지 못했다
- 체결 채널의 토픽을 **실험으로 확정했다**: `realtime-trade:kr`은 `invalid-type`, **`trade:kr`은 수락**. 서버가 구독 응답에 `subscribed`/`rejected`를 돌려주므로 후보를 같이 보내 갈랐다. 다만 **체결 메시지의 실제 모양은 아직 못 봤다**(장중이 아니면 오지 않는다) — 필드 이름은 호가와 같은 규약을 먼저 보고 읽지 못하면 버리며, 앞의 몇 건은 원문을 로그에 남긴다. 그래서 화면 거래량은 여전히 내 체결 수량이다
- `docs/samples/feed-sample.jsonl`은 **합성 샘플**이다. 실제 장의 분포가 아니다

### 7.4 검증의 한계
- `WireLayoutTest`는 **길이 합이 같고 순서만 다른 배치**를 못 잡는다(T4-02). T6-01은 열거값 대조를 더했고, 필드 순서 대조를 더했다는 기록은 없다
- 변이 검사는 **확률에 기대는 경쟁**(T3-07)과 **성립하는 assert**(T3-14)를 확인할 수 없다
- 공유 작업 트리에서는 게이트 결과가 증거가 못 된다 → `git worktree`가 근본 해결(T5-07)
- 접속 풀의 접속 둘 경합은 **재현하지 못했다** — 코드로 확정하고 회귀 테스트만 남겼다(T6-11)
- 부품 테스트가 부품을 직접 부르는 구조에서는 **잇는 줄이 없어도 통과**한다. Phase 6에서 세 번(T6-03·04·10) 나왔고, 줄을 지나가는 테스트로 바꿨지만 모든 줄을 셌다는 보장은 없다
