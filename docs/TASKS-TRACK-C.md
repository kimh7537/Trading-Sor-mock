# Track C — 운영 신뢰성과 이벤트 처리

> 면접에서 깊게 파고들 수 있는 주제를 프로젝트에 자연스럽게 심는 트랙.
> **Phase 2 완료 후 착수 가능.** Phase 3(원장·FEP)와 병행할 수 있다.

---

## 이 트랙의 원칙

**기술을 먼저 정하고 끼워 넣지 않는다.** 문제가 요구해서 도입한 것만 남긴다.

면접관은 "왜 썼는지"를 묻는다. "배우고 싶어서"는 답이 안 된다.
각 태스크마다 **어떤 문제 때문에 필요했는지**를 명시했다.

---

## 증권사 IT에서 각 기술의 실제 위치

**넣어야 할 것** — 증권사 매매 시스템의 핵심 관심사

| 주제 | 실제 위치 |
|---|---|
| 멱등성·중복 방지 | 주문 경로의 기본. 재전송으로 이중 주문이 나가면 사고 |
| 저널링·복구 | 원장 시스템의 전제. 장애 후 상태 복원은 필수 |
| 정합성 대사 | 일일 대사는 증권사 필수 업무. 원장·체결·잔고를 맞춘다 |
| 이벤트 소싱 | 거래 원장이 이미 이 구조. append-only 저널 + 파생 잔고 |
| 성능 측정 | 주문 지연은 직접적 경쟁력. p99가 실제 관리 지표 |
| 보상 트랜잭션 | 분할 주문 취소 등. 이름을 안 붙일 뿐 실제로 쓴다 |

**위치를 가려서 넣을 것**

| 주제 | 맞는 위치 | 틀린 위치 |
|---|---|---|
| Kafka | 정보계 데이터 파이프라인, 알림, 로그 수집 | **주문 핵심 경로** — 지연·순서 보장 때문에 안 씀 |
| CQRS | 계정계(쓰기) / 정보계(읽기) 분리 | 원장 내부를 쪼개는 용도 |
| MSA | 채널계·정보계 일부 | 계정계 원장 — 트랜잭션 경계 때문에 모놀리식이 일반적 |

**주문 경로에 Kafka를 넣으면 감점이다.** 이건 명확히 구분해서 설명할 수 있어야 한다.
"정보계 파이프라인에만 썼고, 주문 경로는 동기 전문으로 유지했다"가 정답이다.

### TC-01 멱등성 — 중복 주문 차단
- [ ] 의존: T2-09

**해결하는 문제**

네트워크 단절 후 클라이언트가 재전송하면 같은 주문이 두 번 들어간다.
FEP 경로에서 응답을 못 받은 클라이언트는 보냈는지 안 보냈는지 모른다.

**완료 조건**
- 클라이언트가 `client_order_id`를 부여 (계좌 + 일자 + 일련번호 조합)
- 원장이 `client_order_id` 기준으로 중복 검사
- 중복 요청에는 **에러가 아니라 원래 응답을 재반환** (멱등 응답)
- 검사 테이블의 보존 기간 정의 (당일 + N일)
- 조회 성능: 해시 인덱스로 O(1)
- `test_idempotency`
  - 동일 요청 2회 → 주문 1건, 응답 동일
  - 응답 유실 시뮬레이션 후 재전송 → 이중 주문 없음
  - 다른 계좌의 동일 일련번호 → 별개 주문으로 처리

**예상 면접 질문**
- 멱등키를 무엇으로 잡았고 왜 그렇게 정했나
- 중복 요청에 에러를 주지 않고 원래 응답을 주는 이유는
- 멱등키 저장소가 죽으면 어떻게 되나

### TC-02 저널링
- [ ] 의존: TC-01

**해결하는 문제**

프로세스가 죽으면 메모리 상태가 사라진다. 미체결 주문과 잔고를 복원해야 한다.

**완료 조건**
- 매칭 엔진·원장에 들어가는 **모든 입력 이벤트**를 append-only 로그에 기록
- 기록 시점: 처리 **전**에 기록하고 fsync (write-ahead)
- 레코드 형식: 길이 + 시퀀스 + 타입 + 페이로드 + 체크섬
- 파일 롤오버 (크기 또는 일자 기준)
- 손상된 레코드 감지 시 그 지점까지만 복구하고 경고
- `test_journal`: 기록 → 재읽기 일치, 중간 절단된 파일 처리, 체크섬 불일치 감지

**설계 포인트**: 처리 후가 아니라 처리 전에 기록해야 한다. 이유를 설명할 수 있어야 한다.

저널이 쌓이면 전체 재생에 시간이 오래 걸린다.

**완료 조건**

- 복구: 최신 스냅샷 로드 → 그 이후 저널만 재생
- 스냅샷 생성 중에도 처리가 멈추지 않을 것 (또는 멈춤 시간을 측정해 명시)
- 복구 결과가 장애 직전 상태와 **완전히 일치** (결정성 덕분에 가능)
- 복구 소요 시간 측정
- `test_recovery`
  - 임의 시점 강제 종료 → 재기동 → 상태 일치 검증
  - 스냅샷 없이 저널만으로 복구
  - 스냅샷 손상 시 이전 스냅샷으로 폴백

**예상 면접 질문**
- 스냅샷 주기를 어떻게 정했나
- 스냅샷 생성 중 들어온 요청은 어떻게 처리하나
- 복구가 결정적이라는 걸 어떻게 보장하나

### TC-04 이벤트 소싱 — 주문 원장
- [ ] 의존: TC-03

**해결하는 문제**

"이 주문이 왜 이 상태가 됐는가"를 사후에 설명해야 한다.
증권사는 민원·감독 대응으로 이력 추적이 필요하다.

**완료 조건**
- 주문의 현재 상태를 저장하는 대신, **상태 변경 이벤트를 저장**
  - `OrderPlaced` → `OrderRouted` → `OrderPartiallyFilled` → `OrderFilled`
  - `OrderRejected`, `OrderCanceled`, `OrderModified`
- 현재 상태는 이벤트를 접어서(fold) 계산
- 임의 시점의 상태를 재구성하는 API: `rebuild_order_state(order_id, until_seq)`
- 이벤트는 불변. 수정·삭제 없음. 정정은 보정 이벤트로
- `test_event_sourcing`
  - 이벤트 시퀀스 → 최종 상태 일치
  - 중간 시점 재구성
  - 이벤트 순서가 뒤바뀐 경우 감지

**설계 판단** (`docs/decisions/`에 기록)
- 전량 이벤트 소싱 vs 현재 상태 캐시 병행 — 조회 성능 트레이드오프
- 이벤트 스키마 변경 시 하위 호환 처리

**예상 면접 질문**
- 이벤트 소싱의 단점은 무엇이고 어떻게 감당했나
- 조회할 때마다 접으면 느리지 않나
- 이벤트 스키마가 바뀌면 과거 이벤트는 어떻게 하나

### TC-05 CQRS — 읽기 모델 분리

**해결하는 문제**

이벤트를 매번 접으면 조회가 느리다. 화면은 빠른 조회가 필요하다.

**완료 조건**

- 읽기 모델: 조회용 프로젝션 테이블 (PostgreSQL)
  - 미체결 목록, 체결 내역, 잔고, 일별 집계
- 프로젝터: 이벤트를 구독해 읽기 모델 갱신
- **최종 일관성 지연을 측정**하고 허용 범위를 명시
- 프로젝션 재구축: 읽기 모델을 비우고 이벤트 전체 재생으로 복원
- `test_projection`
  - 이벤트 → 프로젝션 반영
  - 프로젝션 삭제 후 재구축 → 동일 결과
  - 지연 측정

**증권사 대응**: 계정계(쓰기)와 정보계(읽기)의 분리가 실제로 이 구조다.

**예상 면접 질문**

- 어떤 조회는 쓰기 모델에서 직접 읽어야 하나
- 프로젝터가 죽으면 어떻게 되나

### TC-06 정합성 대사
- [ ] 의존: TC-05

**해결하는 문제**

증권사는 매일 원장·체결·잔고를 대사한다. 어긋나면 사고다.

**완료 조건**
- 대사 항목
  - 주문별: `원수량 == 체결수량 + 잔량 + 취소수량`
  - 계좌별: `잔고 == 초기잔고 + Σ매수체결 − Σ매도체결`
  - 시장별: `매수 체결 합계 == 매도 체결 합계`
  - 논리 주문: `논리 수량 == Σ물리 주문 수량`
  - 읽기 모델: 프로젝션 vs 이벤트 재계산 결과
- 불일치 발견 시 상세 리포트 생성 (어느 주문·계좌·시점인지)
- 일 단위 배치 + 온디맨드 실행
- 의도적으로 불일치를 주입해 탐지되는지 검증
- `test_reconciliation`: 각 대사 항목별 정상·불일치 케이스

**이 태스크가 실제로 버그를 잡는다.** 가장 실용적인 부분이다.

### TC-07 분할 주문 보상 트랜잭션
- [ ] 의존: T2-11, TC-04

**해결하는 문제**

논리 주문 하나가 KRX·NXT 두 물리 주문으로 나뉜다.
취소 요청 시 한쪽은 취소 성공, 다른 쪽은 이미 체결되어 실패할 수 있다.
**원자적 취소가 불가능하다.**

**완료 조건**
- 취소 시나리오 정의
  - 양쪽 취소 성공 → 논리 주문 CANCELED
  - 한쪽 취소 성공, 한쪽 체결 → 논리 주문 PARTIALLY_FILLED. 보상 없음
  - 한쪽 취소 성공, 한쪽 응답 없음 → 상태 미확정. 재조회 후 판정
- 보상 정책을 설정으로 선택 가능하게
  - `NONE` — 부분 체결 그대로 수용 (기본값)
  - `REVERSE` — 체결된 만큼 반대매매로 청산 (옵션, 위험성 명시)
- 각 단계를 이벤트로 기록해 사후 추적 가능
- 타임아웃 및 재시도 정책
- `test_compensation`: 위 시나리오 각각

**주의**: 실제 증권사는 자동 반대매매를 함부로 하지 않는다.
`REVERSE`는 구현하되 기본값은 `NONE`으로 두고, 그 이유를 문서화한다.

**예상 면접 질문**
- 왜 2PC를 쓰지 않았나
- 보상이 실패하면 어떻게 하나
- 사용자에게는 어떤 상태로 보여주나

### TC-08 Kafka 이벤트 파이프라인 (정보계)
- [ ] 의존: TC-05

**해결하는 문제**

체결 데이터를 분석하고 싶지만, 원장에 분석 쿼리를 날리면 매매에 영향을 준다.

**중요**: 주문 핵심 경로에는 Kafka를 넣지 않는다.
체결이 **완료된 후** 정보계로 흘려보내는 용도로만 쓴다.

```
[원장] ──동기 전문──> [FEP] ──> [거래소]     ← 핵심 경로. Kafka 없음
   │
   └── 체결 완료 이벤트 ──> [Kafka] ──> [정보계]   ← 여기만 Kafka
```

**완료 조건**
- 토픽 설계
  - `execution.completed` — 체결 완료
  - `order.lifecycle` — 주문 상태 변경
  - `sor.decision` — 라우팅 판단 근거
- 파티션 키: 종목코드 (종목별 순서 보장)
- 컨슈머: 데이터마트 적재
- **주문 경로 지연에 영향이 없음을 측정으로 증명** (Kafka 도입 전후 p99 비교)
- 컨슈머 장애 시 재처리 (오프셋 관리)
- `test_pipeline`: 이벤트 발행 → 적재 확인, 컨슈머 재시작 후 중복 없이 재개

**예상 면접 질문**
- 왜 주문 경로에는 Kafka를 안 썼나  ← **핵심 질문**
- 파티션 키를 종목코드로 한 이유는
- 컨슈머가 중복 처리하면 어떻게 되나

### TC-10 성능 측정과 개선
- [ ] 의존: TC-03

**해결하는 문제**

"빠르다"는 주관적이다. 숫자가 없으면 개선했는지 알 수 없다.

**완료 조건**
- 구간별 지연 계측 지점 삽입
  - 채널 접수 → 원장 진입
  - 원장 검증
  - SOR 판단
  - FEP 전송 → 거래소 응답
  - 체결 통보 → 클라이언트
- p50 / p95 / p99 / max 산출
- 부하 조건별 측정 (100 / 1,000 / 10,000 TPS)
- **개선 전후 비교를 최소 3건 기록**
  - 예: 저널 fsync 배치화, 공유메모리 락 경합 완화, 호가창 캐시
  - 각각 무엇을 바꿔서 얼마나 개선됐는지
- `bench/results/`에 날짜별 기록

**이력서에 들어갈 문장**: "초당 N건 처리, p99 Nms. 저널 배치화로 p99를 M% 개선."

**예상 면접 질문**
- 병목을 어떻게 찾았나
- p99가 p50보다 훨씬 큰 이유는 무엇이었나
- 더 개선하려면 무엇을 하겠나

### TC-11 장애 주입 테스트
- [ ] 의존: TC-10

**해결하는 문제**

복구 로직은 실제로 죽여봐야 검증된다.

**완료 조건**
- 주입 시나리오
  - 매칭 엔진 강제 종료 (`SIGKILL`)
  - 원장 워커 프로세스 종료
  - FEP 세션 강제 단절
  - 디스크 쓰기 실패 (저널 fsync 실패)
  - Kafka 브로커 중단
- 각 시나리오에서 데이터 유실·중복·불일치가 없음을 확인
- 자동화해 CI에서 실행
- 복구 소요 시간 기록
- 실패한 시나리오와 그 원인, 수정 내역을 문서화

**면접 소재**: "이런 장애를 주입했더니 이런 문제가 드러났고, 이렇게 고쳤다"가
가장 설득력 있는 이야기다. 실패 사례를 숨기지 말고 기록한다.

## 면접 대비 정리

프로젝트를 마친 뒤 아래를 한 장으로 정리해둔다. `docs/INTERVIEW.md`.

**주제별 준비 항목**

| 주제 | 준비할 답변 |
|---|---|
| 자료구조 선택 | 호가창을 배열로 한 이유, 해시 충돌 처리 방식 |
| 결정성 | 왜 필요했고 어떻게 보장했나 |
| 멱등성 | 키 설계, 중복 응답 정책 |
| 저널링 | write-ahead인 이유, fsync 비용 처리 |
| 이벤트 소싱 | 장단점, 조회 성능 대응 |
| CQRS | 최종 일관성 허용 범위, 계정계/정보계 대응 |
| 보상 트랜잭션 | 2PC 대신 선택한 이유 |
| Kafka 위치 | **주문 경로에 안 쓴 이유** |
| 성능 | 병목 발견 과정, 개선 3건 |
| 장애 | 주입 테스트로 드러난 실제 문제 |

**답변 원칙**

- "배우고 싶어서"가 아니라 "이 문제 때문에"로 시작한다
- 트레이드오프를 말한다. 장점만 말하면 깊이가 없어 보인다
- 실패와 수정 내역을 준비한다. 성공담만 있으면 직접 안 한 것처럼 들린다
- 숫자를 준비한다. p99, TPS, 개선폭
