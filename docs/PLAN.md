# 복수시장 주문 집행 시스템 시뮬레이터 기획서

> 코드네임: **mini-sor**
> 작성일: 2026-09-15 (v4)

---

## 1. 왜 이걸 만드는가

### 1.1 출발점

알고리즘 트레이딩 전략을 개발하면서 백테스트와 실거래의 괴리를 확인했다.
백테스트는 "신호 가격에 전량 즉시 체결"을 가정하지만, 실제로는 슬리피지·부분 체결·미체결이 있다.
이 차이가 전략 성과를 뒤집을 수 있는데, 검증할 방법이 없다.

여기에 2025년 3월 넥스트레이드(NXT) 출범으로 변수가 하나 더 생겼다.

**같은 종목이 KRX와 NXT 두 시장에서 거래되고, 어느 시장에서 체결되느냐에 따라 결과가 달라진다.**

- 두 시장의 호가와 잔량이 다르다
- 거래 시간이 다르다 (KRX 09:00~15:30 / NXT 08:00~20:00)
- 수수료가 다르다
- NXT에는 중간가 주문 같은 KRX에 없는 주문 유형이 있다

그런데 개인 투자자는 이 배분을 통제하지 못한다. 증권사 API로 주문을 내면
증권사가 자체 SOR로 시장을 나눠 보낸다. **내 주문이 어디로 갔는지, 그 선택이 내 전략에
유리했는지 알 수 없다.**

### 1.2 목표

**복수시장 환경의 주문 집행을 직접 구현해, 전략 검증에 쓰고 결과를 측정한다.**

1. 규칙이 다른 두 개의 매칭 엔진(KRX형 / NXT형)을 구현한다
2. 최선집행기준을 정의하고 주문을 배분하는 SOR 엔진을 만든다
3. 이를 백테스트의 체결 계층으로 사용해 낙관적 가정을 제거한다
4. 집행 전략별 결과를 비교해, 증권사 SOR이 내 전략에 유리한지 판단할 근거를 얻는다
5. 화면에서 양 시장 호가와 배분 판단을 직접 확인한다

### 1.3 두 가지 용도

이 프로젝트는 목적이 둘이다. 억지로 하나로 합치지 않고, 공존을 인정한다.

| 용도 | 내용 | 필요 범위 |
|---|---|---|
| **개인 활용** | 백테스트 체결 시뮬레이터, 페이퍼 트레이딩, 스트레스 테스트 | Phase 1~2 + Track B |
| **기술 증명** | 증권사 매매 시스템 전 계층 구현 | Phase 1~5 |

공통 구간은 Phase 1~2다. 이후 목적에 따라 갈린다.

**실거래 경로에 mini-sor는 끼지 않는다.** 주문은 토스증권 API가 처리한다.
mini-sor의 쓰임새는 실거래 이전 단계(검증)와 사후 분석이다.

### 1.4 이 주제의 의미

매칭 엔진은 증권사가 만들지 않는다. 매칭은 거래소가 한다.
하지만 **SOR을 만들려면 매칭 엔진을 이해해야 한다.**
호가 잔량이 어떻게 소진되는지, 내 주문이 대기열 어디에 들어가는지 모르면
"어느 시장이 유리한가"를 판단할 수 없다.

그리고 SOR은 증권사 IT가 지금 실제로 풀고 있는 과제다.

- 자본시장법 제68조 최선집행의무에 따라 증권사는 최선집행기준을 수립하고 SOR을 운영해야 한다
- 자본시장연구원 분석 기준, 2025년 4월 초 시점에 국내 50개 증권사 중
  SOR 기반 양 시장 집행을 하던 곳은 15개사였다
- 업계 전반에서 아직 성숙 단계가 아니며 구현 방식 차이가 크다

### 1.5 비목표

- 실거래 주문 집행 (토스증권 API 담당)
- 전략 로직 자체 (별도 프로젝트, Track B에서 연동)
- 청산·결제 (실제로도 KRX가 일괄 수행)
- 파생상품, 신용·대주

착수할 수 있게 만든다.

## 3. 핵심 설계

### 3.1 ④ SOR 엔진 (C)

**통합 호가창 (Consolidated Order Book)**

양 시장 호가를 하나로 합쳐 관리한다. 각 가격 레벨에 시장별 잔량을 함께 보유한다.

```c
typedef struct {
    int32_t price;
    int32_t qty_krx;
    int32_t qty_nxt;
} consolidated_level_t;
```

갱신 지연이 곧 판단 오류가 되므로 갱신 경로의 지연을 별도로 측정한다.

**최선집행기준 평가**

| 항목 | 내용 |
|---|---|
| 가격 | 시장별 최우선 반대호가 |
| 체결 가능성 | 해당 가격대 잔량, 최근 체결 빈도 |
| 거래 비용 | 시장별 수수료율 |
| 시장 상태 | 현재 시각에 해당 시장이 열려 있는가 |

가중치는 설정 파일로 분리한다. 증권사마다 기준이 다르다는 점을 반영한 설계다.

**집행 전략 (비교 대상)**

| 전략 | 동작 |
|---|---|
| KRX_ONLY | 전량 KRX (기준선) |
| BEST_PRICE | 최우선 가격이 유리한 한 시장에 전량 |
| SPLIT | 양 시장 잔량에 비례 분할 |
| SWEEP | 유리한 시장부터 잔량만큼 채우고 나머지를 다른 시장으로 |

같은 주문을 네 전략으로 집행해 평균 체결 단가와 체결률을 비교한다.

**판단 근거 기록**

모든 라우팅 결정에 대해 판단 시점의 양 시장 호가, 계산된 점수, 선택 이유를 기록한다.
최선집행의무는 "가장 유리한 결과"가 아니라 "가장 유리한 판단 기준"을 요구한다.
따라서 결과보다 근거의 기록이 중요하다.

**분할 주문의 어려움**

의도적으로 정면으로 다룬다.

- 한쪽만 체결되고 다른 쪽이 거부되면? → 부분 집행 상태 관리
- 취소 요청 시 양쪽을 어떻게 원자적으로 취소할 것인가
- 한쪽 취소 성공, 다른 쪽 실패 시 보상 처리
- 화면에는 한 줄로 보여야 한다 → 논리 주문 ↔ 물리 주문 매핑

### 3.2 ⑥ 매칭 엔진 (C) — 두 개, 규칙이 다르다

**공통**

- 가격 우선 → 시간 우선
- 지정가, 시장가, IOC, FOK
- 부분 체결, 잔량 호가 등록
- 가격 제한폭 ±30%

**KRX 시뮬 고유**: 정규장 09:00~15:30. 단일가 매매는 미구현.

**NXT 시뮬 고유**

- 프리마켓 08:00~08:50 / 메인 09:00:30~15:20 / 애프터 15:30~20:00
- 프리·애프터마켓은 지정가만 허용
- 휴장 구간(08:50~09:00:30, 15:20~15:30)은 신규·정정 불가, 취소만 가능
- **중간가 주문**: 가격을 (최우선매수 + 최우선매도) ÷ 2로 자동 결정

중간가 주문이 특히 구현할 가치가 있다. 기준가가 호가 변동에 따라 움직이므로
일반 지정가 매칭과 다른 처리가 필요하다.

**결정성**

두 엔진 모두 단일 스레드, 시스템 시각 비의존, 논리 시각만 사용.
같은 입력에 같은 출력이 나와야 전략 비교와 백테스트 재현이 성립한다.

**유동성 공급**

| 모드 | 내용 |
|---|---|
| Instant | 요청 가격에 전량 즉시 체결. 낙관적 기준선 |
| Synthetic | 포아송 도착 + 지수 분포 가격의 가상 참가자 |
| Divergent | 두 시장에 의도적으로 다른 유동성 부여 |
| Replay | 수집한 과거 호가 데이터 재생 |

Instant는 기존 백테스트와 동일한 가정이다. Divergent와의 차이가 곧 측정 대상이다.
Divergent가 없으면 SOR을 검증할 수 없으므로 우선순위가 높다.

### 3.3 ③ 원장 (C)

**프로세스 구조**

- 리스너 1 + 워커 풀 N (사전 fork)
- 공유메모리: 계좌 잔고, 미체결 주문 인덱스
- 세마포어로 계좌 단위 동시성 제어

TP 모니터를 만들지는 않는다. 프레임워크가 감춰둔 구조를 직접 구현해
동작 원리를 확인하는 것이 목적이다.

**전문 구조 (자체 설계)**

```
공통 헤더 (64 byte)
┌────────┬────────┬────────┬──────────┬────────┬────────┬────────┐
│전문길이 │전문종별 │기관코드 │ 계좌번호  │일련번호 │전송일시 │응답코드 │
│  (6)   │  (8)   │  (4)   │   (11)   │  (10)  │  (14)  │  (4)   │
└────────┴────────┴────────┴──────────┴────────┴────────┴────────┘
```

전 필드 고정 길이. 구조체 직접 매핑, `#pragma pack(1)`.

**검증 로직**

- 계좌 유효성, 거래 가능 여부
- 매수: 주문금액 + 수수료 ≤ 주문가능금액
- 매도: 주문수량 ≤ 보유수량 − 기매도주문수량
- 가격 제한폭, 호가 단위 적합성
- **시장별 거래 가능 종목 여부** — 복수시장 환경의 특징

### 3.4 ⑤ FEP (C) — 두 개

시장마다 별도 프로세스. 프로토콜도 다르게 설계해 변환 계층의 의미를 만든다.

- `epoll` 기반 논블로킹 이벤트 루프
- 부분 수신 처리 (수신 버퍼에서 전문 길이를 읽어 조립)
- 송신 큐 및 `EAGAIN` 처리
- 세션 로그인, 하트비트, 재접속
- 시퀀스 갭 감지 및 재전송 요청
- 내부 주문번호 ↔ 시장 주문번호 매핑

**핵심 과제**: 세션 단절 시 미응답 주문의 상태 판정.
보냈는지 안 보냈는지 모르는 주문을 어떻게 처리할 것인가.

### 3.5 ② 채널계 (Java / Spring Boot)

얇게 유지한다. 비즈니스 로직은 넣지 않는다.

- REST ↔ 고정 길이 전문 변환 (어노테이션 기반 매핑 유틸 자체 제작)
- 원장과의 TCP 커넥션 풀
- WebSocket 실시간 배포

### 3.6 ① 프론트엔드 (React)

```
┌──────────────┬──────────────┬─────────────────────┐
│  KRX 호가창   │  NXT 호가창   │   주문 입력          │
│  매도 10단    │  매도 10단    │   집행전략 선택       │
│  ──────────  │  ──────────  │                     │
│  매수 10단    │  매수 10단    ├─────────────────────┤
│  ※ 유리한 쪽  │              │   SOR 판단 근거      │
│    하이라이트  │              │   시장별 점수·이유    │
├──────────────┴──────────────┼─────────────────────┤
│  미체결 (논리주문 → 물리주문)   │   체결 내역 / 잔고   │
└─────────────────────────────┴─────────────────────┘
```

- SOR 판단 근거 패널이 이 프로젝트의 얼굴
- 별도 화면: 집행 전략 비교, 백테스트 결과, 관제

## 4. 진행 경로

### 4.1 Phase 구성

| Phase | 내용 | 원안 | Claude Code |
|---|---|---|---|
| 1 | 매칭 엔진 2종 | 5~6주 | 3~4주 |
| 2 | SOR 엔진 | 4~5주 | 3~4주 |
| **Track B** | **백테스트 연동** | — | **4~6주** |
| 3 | 원장 + FEP | 5~6주 | 4~5주 |
| 4 | 채널계 + 프론트엔드 | 4~5주 | 1.5~2주 |
| 5 | 안정화 | 4주 | 2~3주 |

주당 10~15시간 기준. 전체 완주 시 3.5~4.5개월.

Claude Code의 효과는 구간마다 다르다. Phase 4(채널계·프론트)는 절반 이하로 줄지만,
Phase 3(멀티프로세스·공유메모리·epoll)은 디버깅이 병목이라 크게 줄지 않는다.

### 4.2 분기

```
Phase 1 (매칭 엔진)
    ↓
Phase 2 (SOR)
    ↓
    ├──────→ Track B (백테스트 연동)        ← 개인 활용
    │             4~6주
    │
    ├──────→ Track C (운영 신뢰성·이벤트)    ← 면접 대비
    │             4~6주 · Phase 3과 병행 가능
    │
    └──────→ Phase 3 (원장+FEP)             ← 기술 증명
                  ↓
             Phase 4 (채널계+프론트)
                  ↓
             Phase 5 (안정화)
```

**Phase 1+2가 공통 구간이다.** Claude Code 기준 6~8주.
여기까지만 해도 "매칭 엔진 2종 + SOR + 집행 전략 비교 실험"으로 완결된 결과물이 된다.

**Track B는 Phase 3을 필요로 하지 않는다.** 백테스트 경로가 원장·FEP를 우회하기 때문이다.
개인 활용을 먼저 보고 싶다면 Phase 2 → Track B → Phase 3 순서가 가능하다.

**Track C는 Phase 3과 병행한다.** 멱등성·저널링·정합성은 원장 구현과 맞물리는 주제라
Phase 3 태스크와 섞어서 진행하는 편이 자연스럽다.
Track C의 우선순위 1~4번(멱등성, 저널링·복구, 정합성 대사, 성능 측정)은
증권사 IT의 핵심 관심사이므로 어느 경로를 택하든 포함시킨다.

**일정에서 역산한다.**

| 남은 기간 | 권장 범위 |
|---|---|
| 1개월 | Phase 1 + SOR 최소 구현. 나머지는 전부 제외 |
| 2~3개월 | Phase 1+2 + Track C 우선순위 1~4 |
| 4개월 | 위 + Track B 또는 Phase 3 택일 |
| 6개월 이상 | 전체 |

**코드 이해 시간을 일정에 포함한다.** Claude Code로 생성하는 시간보다
생성된 코드를 설명할 수 있을 만큼 읽는 시간이 길다. 이 시간은 줄이면 안 된다.
설명하지 못하는 코드는 포트폴리오에서 감점 요인이다.

### 4.3 Track B 개요

상세는 `docs/TASKS-TRACK-B.md`.

**용도**

| 역할 | 내용 |
|---|---|
| 체결 시뮬레이터 | 백테스트의 체결 계층 교체. 슬리피지·부분체결 반영 |
| 페이퍼 트레이딩 | 실계좌 투입 전 검증. 장 시간 무관, 반복 실행 |
| 스트레스 테스트 | 유동성 고갈·가격 역전 시 전략 반응 확인 |
| 집행 전략 실험 | 증권사 SOR이 내 전략에 유리한지 판단할 근거 |

**설계 원칙**

전략 코드는 붙은 대상을 모른다. 브로커 인터페이스 하나에 구현체 둘(mini-sor / 토스증권).
시각은 주입받는다. 백테스트는 가상 시계로 3개월치를 몇 분에 돌린다.

### 4.4 Track C 개요

상세는 `docs/TASKS-TRACK-C.md`.

면접에서 깊게 다룰 수 있는 주제를 프로젝트에 자연스럽게 심는 트랙.
**기술을 먼저 정하고 끼워 넣지 않는다.** 문제가 요구해서 도입한 것만 남긴다.

**증권사 IT에서의 위치**

| 주제 | 실제 위치 |
|---|---|
| 멱등성·중복 방지 | 주문 경로의 기본. 재전송으로 이중 주문이 나가면 사고 |
| 저널링·복구 | 원장 시스템의 전제 |
| 정합성 대사 | 일일 대사는 증권사 필수 업무 |
| 이벤트 소싱 | 거래 원장이 이미 이 구조 (append-only + 파생 잔고) |
| CQRS | 계정계(쓰기) / 정보계(읽기) 분리와 대응 |
| 보상 트랜잭션 | 분할 주문 취소. 이름을 안 붙일 뿐 실제로 씀 |
| 성능 측정 | 주문 지연은 직접적 경쟁력 |

**Kafka의 위치를 가린다**

```
[원장] ──동기 전문──> [FEP] ──> [거래소]     ← 핵심 경로. Kafka 없음
   │
   └── 체결 완료 이벤트 ──> [Kafka] ──> [정보계]   ← 여기만 Kafka
```

주문 핵심 경로는 지연과 순서 보장이 생명이라 메시지 브로커를 끼우지 않는다.
Kafka는 체결 완료 후 정보계로 흘려보내는 용도로만 쓴다.
**"왜 주문 경로에는 Kafka를 안 썼나"가 이 트랙에서 가장 값진 면접 질문이다.**

## 7. 리스크

| 리스크 | 대응 |
|---|---|
| 전체 3.5~4.5개월 | Phase 1+2(6~8주)만으로 독립 완결 |
| C 메모리·동시성 디버깅 | ASan/Valgrind 초기 적용, 단위 테스트 우선 |
| 두 목적의 충돌 | 공통 구간(Phase 1+2) 이후 분기. 억지로 합치지 않음 |
| Claude Code 의존 | 설계 판단은 직접 내리고 `docs/decisions/`에 기록. 코드를 설명할 수 없으면 프로젝트 가치가 없음 |
| 토스증권 API 제약 | 브로커 인터페이스를 실거래 쪽 제약에 맞춰 좁게 설계 |
| 실제 규정과의 차이 | 완전 재현이 목표가 아님. 단순화 지점을 문서에 명시 |
| 회사 업무와의 경계 | 공개 자료·자체 설계만 사용. 업무상 접한 전문 규격·소스 일절 미반영 |
