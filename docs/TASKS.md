# 작업 목록

각 태스크는 한 세션에 끝낼 수 있는 크기다.
완료 조건이 곧 테스트 명세다. 완료 조건에 없는 것은 만들지 않는다.

**진행 규칙**
- `[ ]` → `[x]`로 바꾸는 것은 전체 테스트 + ASan 통과 후에만
- 의존성(`의존:`)이 미완료면 해당 태스크를 시작하지 않는다
- 한 세션에 한 태스크

### T3-04 워커 프로세스 풀 (사전 fork)

`ledger/worker_pool.{h,c}`

**완료 조건**

  않는다 — 사전 fork가 이 태스크의 제목이다
- 워커가 **소켓을 어떻게 나눠 갖는지 정하고 근거를 문서화한다**
  (fd 전달 / 공유 리스닝 소켓 / `SO_REUSEPORT`)

- 워커별 처리 건수를 보고한다 — 분배가 실제로 일어났는지 확인할 수 있어야 한다

### T3-05 공유메모리 세그먼트 설계 및 초기화

- 배치를 표로 문서화한다. **포인터를 저장하지 않는다** — 오프셋으로 접근

  사전 fork 풀에서 워커는 죽을 수 있다(T3-04가 다시 띄운다).
  회수하지 못하면 그 계좌가 영영 막힌다
- 잔고 불변조건: `0 <= reserved <= cash`. 어기는 연산은 **거절하고 아무것도
  바꾸지 않는다**
- 증거금 묶기·풀기·정산이 원자적이다 — 중간에 죽어도 절반만 반영되지 않는다
- `test_account.c`: 실제 fork로 두 프로세스가 같은 계좌를 갱신하는 것,
  **락을 쥔 채 죽는 경우**를 포함

### T3-07 주문 검증 로직 (증거금·한도·호가단위·거래가능종목)
- [x] 의존: T3-06

`ledger/order_validate.{h,c}`

**완료 조건**
- 네 가지를 본다: **거래가능종목 / 호가단위 / 주문 한도 / 증거금**
- **검사 순서를 정하고 근거를 문서화한다.** 계좌 락은 워커끼리 부딪히는 유일한

- **증거금 확인과 묶기가 한 번에 일어난다.** 확인하고 나서 따로 묶으면 그 사이에

### T3-08 FEP 공통 — epoll 이벤트 루프
- [x] 의존: T3-02

`fep/evloop.{h,c}`

**완료 조건**
- `epoll`로 여러 fd를 **동시에** 감시한다. fd마다 콜백과 컨텍스트를 붙인다
- **레벨 트리거인지 에지 트리거인지 정하고 근거를 문서화한다**
- 등록·변경·해제가 된다. 해제한 fd는 더 이상 콜백을 받지 않는다
- **논블로킹 소켓을 쓴다** — 상대 하나가 느려도 루프가 멈추지 않는다
- **콜백 안에서 fd를 닫아도 루프가 깨지지 않는다.** `epoll_wait`이 돌려준 한
  묶음 안에 그 fd의 이벤트가 또 들어 있을 수 있다
- 멈춤 신호에 빠져나온다
- `test_evloop.c`: 소켓 여러 개에서 동시에 읽기, 콜백 안에서 닫기, 멈춤

### T3-09 FEP 공통 — 전문 조립 (부분 수신 처리)
- [x] 의존: T3-08

`fep/framer.{h,c}`

**완료 조건**
- **TCP는 전문 경계를 지켜 주지 않는다.** 받은 바이트를 쌓아 두고 완성된 전문만
  꺼낸다. 헤더 24바이트가 세 번에 나뉘어 와도 조립한다
- **한 번에 두 개 이상 도착해도 각각 꺼낸다.** 꺼낼 게 없을 때까지 반복할 수 있다
- **전문마다 할당하지 않는다.** 접속 하나에 버퍼 하나를 재사용한다
- `body_len`이 한도를 넘으면 **버퍼에 담기 전에** 거절한다
- **magic·version이 어긋났을 때 무엇을 할지 정하고 근거를 문서화한다**
  (재동기할 것인가, 접속을 끊을 것인가)
- 꺼낸 전문의 body 포인터가 **언제까지 유효한지** 문서화한다
- `test_framer.c`: 헤더 쪼개기, 바디 쪼개기, 한 번에 여러 개,
  **1바이트씩 흘려 넣기**(경계 전수), 한도 초과, 어긋난 magic

### T3-10 FEP 공통 — 송신 큐 및 EAGAIN 처리
- [x] 의존: T3-09

`fep/sendq.{h,c}`

**완료 조건**
- 논블로킹 소켓의 `write`는 **일부만 쓰고 EAGAIN을 준다.** 남은 것을 들고 있다가
  다시 쓸 수 있을 때 이어 보낸다. **부분 쓰기는 에러가 아니다**
- **전문을 반만 넣지 않는다.** 자리가 모자라면 통째로 거절한다 — 반쪽 전문이
  나가면 받는 쪽은 T3-09의 판단대로 접속을 끊는다
- 큐가 가득 찼을 때 **무엇을 버릴지가 아니라 누구에게 알릴지**를 정하고
  문서화한다 (주문 전문을 조용히 버리면 안 된다)
- **`EV_WRITE`를 언제 켜고 끌지 정하고 문서화한다.** 레벨 트리거에서 계속 켜
  두면 소켓이 거의 항상 쓸 수 있으므로 루프가 헛돈다
- 상대가 끊긴 경우(EPIPE·ECONNRESET)를 EAGAIN과 **구분해서** 알린다
- `test_sendq.c`: **소켓 버퍼를 작게 잡아 실제로 부분 쓰기를 만든다**,
  이어 보내기, 자리 부족 시 전부 거절, `EV_WRITE` 켜짐·꺼짐, 상대 종료

### T3-11 FEP — 세션 로그인·하트비트·재접속
- [x] 의존: T3-10

`fep/session.{h,c}` (+ `core/msg.h`에 로그인·하트비트 종별 추가)

**완료 조건**

- 로그인·하트비트 전문 종별을 `MSG_TYPE_LIST`에 더한다 (지금은 없다)
- **로그인 전에는 업무 전문을 보내지 않는다.** 상대가 세션을 인정하기 전에 보낸

- **소켓을 누가 만드는지 정하고 문서화한다** (세션인가 호출부인가)

### T3-12 FEP — 시퀀스 갭 감지 및 재전송
- [x] 의존: T3-11

`fep/seqtrack.{h,c}` (+ `core/msg.h`에 재전송 종별 추가, `fep/session.c`에 연결)

**완료 조건**
- 받은 전문의 `seq`를 기대값과 대조해 **갭을 감지한다**

- 갭이 채워지면 **막힌 흐름이 다시 흐른다**
- `test_seqtrack.c`: 정상·중복·갭·되돌아온 seq, 보관 고리가 한 바퀴 돈 뒤
- `test_session.c`에 전 구간: 갭을 만들어 재전송 요청이 나가고, 채워지면
  업무 전문이 다시 위로 올라오는 것

### T3-13 FEP — 주문번호 매핑

### T3-14 세션 단절 시 미응답 주문 상태 판정
- [x] 의존: T3-13

`fep/ordmap.{h,c}` 확장 (+ `core/msg.h`의 조회 응답)

**완료 조건**
- 끊긴 순간 **응답을 못 받은 주문**(`ORD_PENDING`)은 세 가지 중 어느 것인지
  알 수 없다: 거래소가 못 받았다 / 받고 접수했다 / 받고 거부했다

- **조회 응답이 끝났음을 어떻게 아는지 정하고 문서화한다.** 끝을 모르면

- 판정이 안 된 주문이 **몇 건인지 밖에서 볼 수 있다.** 그 수가 0이 아니면
  사람이 알아야 한다
- 조회가 또 끊기면 **판정 보류 상태가 그대로 남는다.** 잃어버리지 않는다
- `test_ordmap.c`: 단절 시 상태 전이, 조회로 접수/거부 판정, **응답에 없던
  주문의 판정**, 조회 중 재단절, 판정 보류 건수

- **풀이 비었을 때 무엇을 할지 정하고 문서화한다.** 무한정 늘리지 않는다
- **깨진 접속을 풀에 되돌리지 않는다.** 되돌리면 다음 요청이 그것을 집는다
- **응답이 제때 안 오면 그 접속을 버린다.** 원장이 처리했는지 안 했는지
  모르는 상태이고, 같은 접속을 계속 쓰면 **응답이 한 칸씩 밀린다**
- 체결 통보처럼 **요청 없이 밀려오는 전문**을 이 풀이 어떻게 다룰지 정하고
  문서화한다 (같은 접속인가, 따로인가)
- 설정(호스트·포트·타임아웃)은 T4-01의 `LedgerProperties`에서 읽는다
- 테스트: 왕복, 풀 재사용, 응답 지연 시 접속 버리기, 원장이 죽었을 때,
  풀 고갈, **동시 요청이 서로 응답을 바꿔 받지 않는 것**

### T4-04 REST API (주문·조회)
- [x] 의존: T4-03

`channel/src/main/java/com/minisor/channel/api/`

**완료 조건**
- 주문 접수·취소·조회를 HTTP로 받는다. 요청을 전문으로 바꿔 원장에 보내고
  응답을 돌려준다
- **입력을 경계에서 검증한다.** 원장(T3-07)이 또 검증하지만, 그것을 믿고
  넘기면 **틀린 주문이 네트워크를 한 번 왕복한 뒤에야 거절된다**
- **원장의 거절 사유를 HTTP 상태로 옮기는 규칙을 정하고 문서화한다.**
  전부 500으로 뭉개면 "내 잘못"과 "서버 잘못"이 구분되지 않는다
- **원장이 죽었을 때와 주문이 거절됐을 때를 다르게 답한다**
- 응답이 오지 않은 주문(T3-14의 모호함)을 **성공으로도 실패로도 단정하지
  않는다.** 무엇으로 답할지 정하고 문서화한다
- 테스트: 정상 주문, 입력 오류, 원장 거절, 원장 사망, 응답 없음

## Phase 5 — 안정화 및 전략 연동 (목표 4주)

### T5-01 저널링 (append-only 입력 로그)
- [x] 의존: 없음

`core/journal.{h,c}`

**완료 조건**
- 입력 사건을 **덧붙이기만 하는** 파일에 적는다. 지우거나 고치지 않는다

- 재생이 **원본과 같은 순서·같은 내용**을 돌려준다
- **언제 디스크에 밀어 넣을지 정하고 근거를 문서화한다** (매번인가 묶음인가)

### T5-02 스냅샷 및 재기동 복구
- [x] 의존: T5-01

`core/snapshot.{h,c}`

**완료 조건**
- 어느 시점의 상태를 파일로 남기고, 재기동 때 그것부터 시작한다
- **스냅샷이 저널의 어디까지를 담았는지 함께 적는다.** 그것 없이는 어디서부터
  이어 재생할지 알 수 없고, 처음부터 재생하면 **두 번 반영된다**
- **스냅샷 쓰기가 원자적이어야 한다.** 쓰다 죽어서 반쪽 스냅샷이 남으면,
  그것을 읽고 시작한 시스템은 조용히 틀린 상태로 돈다
- **스냅샷이 깨졌으면 무시하고 저널만으로 복구한다.** 반쯤 믿지 않는다
- 복구가 **스냅샷 + 이후 저널**을 합쳐 원래 상태를 되살린다
- 테스트: 왕복, 이어 재생, 깨진 스냅샷, 스냅샷 없음, **쓰다 죽은 경우**

### T5-03 정합성 대사 (잔고↔체결↔원장, 논리↔물리)
- [x] 의존: T2-05, T3-06

`core/recon.{h,c}`

**완료 조건**
- **대사는 대상의 코드를 쓰지 않는다. 숫자를 받아서 다시 계산한다.**
  `omap_get()`을 불러 다리 합을 얻으면, `omap`이 합을 잘못 세고 있을 때
  대사도 같이 잘못 세고 "일치"라고 답한다. 그것은 대사가 아니다
- 논리↔물리: 다리들의 **보낸 수량 합이 주문 수량과 같다**. 다리마다
  체결+취소가 보낸 수량을 넘지 않는다. 남아 있다면(`live`) 남은 수량이 있다.
  체결이 0인데 체결 금액이 있으면 안 된다. 물리 번호가 겹치면 안 된다
- 잔고↔체결↔원장: **예수금이 처음 값에서 입출금과 체결로 설명된다.**
  묶인 금액이 미체결 주문들의 몫과 같다. 묶인 금액이 예수금을 넘지 않는다
- **첫 번째 어긋남에서 멈추지 않는다.** 하나만 보고하면 나머지는 다음 대사
  때까지 안 보인다. 찾은 것을 다 담아 돌려준다
- 어긋남마다 **어느 주문·어느 계좌의 무엇이 얼마만큼 틀렸는지** 담는다.
  "안 맞는다"만으로는 아무도 고치지 못한다
- 실제 주문 흐름에서 뽑은 숫자로도 한 번 돌려 본다 (합성 숫자만으로는
  대사가 실제 자료 모양과 맞는지 알 수 없다)
- 테스트: 맞는 경우, 어긋남 종류별, **여러 개가 한꺼번에**, 담을 자리 부족
### T5-04 장애 주입 테스트 (프로세스 강제 종료)
- [x] 의존: T5-01, T5-02, T5-03

`core/tests/test_fault_inject.c`

T5-01은 손으로 자른 파일을 먹였고, T5-02는 손으로 만든 `.tmp`를 놓았다.
**여기서는 진짜로 `SIGKILL`을 놓는다.** 뒷모습을 흉내 낸 것과 실제로 그
일이 일어난 것은 다르다.

(계좌 잠금을 쥔 채 죽는 경우는 `ledger/tests/test_account.c`가 이미 다룬다.
겹쳐 쓰지 않는다.)

**완료 조건**
- **`fsync`까지 끝난 레코드는 `SIGKILL`로도 사라지지 않는다.** 자식이
  레코드를 적고 공유 카운터를 올리면, 부모는 그 수를 보고 죽인다 —
  재생이 **정확히 그 수**를 돌려줘야 한다
- **죽는 시점을 고를 수 없으므로 여러 번 죽여 본다.** 스냅샷을 쉬지 않고
  쓰는 자식을 서로 다른 시점에 반복해 죽이고, 그때마다 원래 자리가
  **온전한 스냅샷이거나 옛 스냅샷**임을 확인한다. 반쪽인 적이 없다
- **죽은 뒤 복구가 선다.** 스냅샷 + 그 이후 저널로 되살린 상태가
  죽기 전과 같고, T5-03의 대사를 통과한다
- 자식이 남긴 것(`.tmp` 등)을 **발견한 그대로 기록한다.** 치워 주는 사람이
  없다는 사실을 테스트가 숨기면 안 된다
- 테스트가 매달리지 않는다. 기다림에는 모두 상한을 둔다
### T5-05 부하 테스트 및 전 구간 성능 측정
- [x] 의존: T5-01, T5-04

`bench/bench_pipeline.c`, `bench/results/pipeline-<날짜>.md`

T1-20은 **매칭 엔진만** 쟀다. 3.8M TPS라는 숫자는 그 조각만의 것이고,
주문 한 건이 실제로 지나는 길에는 원장 검증도 저널도 라우팅도 있다.
**조각의 속도를 전체의 속도로 읽으면 안 된다.**

**완료 조건**
- 주문 한 건이 지나는 **단계를 나눠서 잰다.** 전문 해석 → 원장 검증 →
  저널 기록 → SOR 계획 → 논리↔물리 등록 → 매칭 → 체결 반영
- 단계마다 p50 / p95 / p99. **평균을 쓰지 않는다** — 비용이 균일하지
  않아서 평균이 꼬리를 감춘다 (T1-20과 같은 이유)
- **가장 비싼 단계를 이름으로 지목한다.** "전 구간 N μs"만 적으면
  어디를 고쳐야 하는지 아무도 모른다
- **저널을 켠 경우와 끈 경우를 나란히 잰다.** T5-01이 "매 레코드 `fsync`"를
  고른 대가가 얼마인지는 재기 전에는 아무도 모른다. 숫자를 보고 나서
  그 선택을 다시 판단할 수 있어야 한다
- 부하: 예열을 빼고 최소 2만 건. 처리량(TPS)도 함께
- **하네스가 시스템 시각을 읽되 엔진은 읽지 않는다.** 날짜는 인자로 받는다
  (T2-14의 `compare_write_md`와 같은 규칙)
- 결과를 `bench/results/`에 마크다운으로 남긴다. 측정 조건(CPU·빌드·시드·
  건수)을 같이 적는다 — 조건 없는 숫자는 근거가 아니다
- `ctest`에 넣지 않는다. Release에서 손으로 돌린다
### T5-06 전략 엔진용 시세 피드 규격
- [x] 의존: T1-06, T3-01

`core/feed.{h,c}`

바깥에서 붙는 전략 엔진이 받아 갈 시세 형식. **주문 전문(T3-02)과 다른
채널이다** — 한 방향이고, 요청이 없고, 여럿이 같은 것을 받는다.

**완료 조건**
- 종별은 둘만 둔다: **호가 스냅샷**과 **체결**. 증분(델타)을 두지 않는다.
  왜 안 두는지 근거를 헤더에 적는다
- 시장(KRX/NXT)과 종목을 구분한다. 어느 시장의 호가인지 모르면 SOR을
  흉내 낼 수 없다
- 시퀀스 번호로 **빠짐을 알 수 있다.** 그리고 **빠졌을 때 무엇을 할지
  정하고 근거를 적는다** — 방송 채널이라 재전송을 요청할 상대가 없다.
  T3-12의 답(재전송 요청)을 그대로 쓸 수 없는 자리다
- **모든 시각은 논리 시각이다.** 피드를 만드는 쪽도 읽는 쪽도 시스템 시각을
  읽지 않는다. 읽으면 같은 입력이 같은 피드를 만들지 않는다
- 바이트 배치는 빅엔디언 고정 길이, 바이트 단위로 쓴다 (T3-01의 규칙).
  구조체를 그대로 내보내지 않는다
- 호가창에서 스냅샷 메시지를 만드는 함수를 둔다. 전략 엔진이 호가창 내부
  자료구조를 알 필요가 없어야 한다
- 테스트: 왕복, 단 수 경계(0단·최대단), 짧은 버퍼·긴 버퍼, 빠짐 판정
  (정상·중복·갭), **같은 호가창이 같은 바이트를 만든다**
