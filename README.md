# mini-sor

복수시장(KRX / NXT) 주문 집행 시스템 시뮬레이터

---

## 무엇인가

2025년 3월 넥스트레이드(NXT) 출범으로 국내 주식은 두 시장에서 거래된다.
증권사는 자본시장법 제68조 최선집행의무에 따라 주문을 유리한 시장으로 배분(SOR)해야 한다.

이 프로젝트는 그 환경을 축소 재현한다.

- 규칙이 다른 두 개의 매칭 엔진 (KRX형 / NXT형)
- 그 위에서 주문을 배분하는 SOR 엔진과 집행 전략 4종
- 증권사 원장·FEP 계층
- 양 시장 호가·잔고·미체결을 한 화면에서 보고, 주문 전 예상 체결과 원장이 실제로 나눈 결과(시장별 다리)를 비교하는 화면. 주문·취소, 나중 체결과 잔고 변화는 실시간으로 밀려온다

**만든 이유**: 알고리즘 트레이딩 백테스트가 "신호 가격에 전량 즉시 체결"을 가정하는데,
실제로는 슬리피지·부분 체결·미체결이 있다. 그 차이를 측정하려면 현실적인 체결 환경이 필요했다.

## 결과

전부 `bench/results/`의 파일에서 옮긴 값이다. 같은 시드로 다시 돌리면 같은 표가 나온다.

**집행 전략 — 시드 30개, KRX_ONLY 대비** ([`quality-2026-09-16.md`](bench/results/quality-2026-09-16.md))

| 시나리오 | 복수시장 전략(BEST_PRICE·SPLIT·SWEEP) | 체결률 p50 (KRX_ONLY → 복수시장) |
|---|---|---|
| BALANCED | 22승 5패 3무, 중앙값 +2bp | 52.31% → 100.00% |
| KRX_THIN | 30승 0패 0무, 중앙값 +6bp | 5.27% → 59.46% |
| NXT_THIN | 0승 25패 5무, 중앙값 -1bp | 52.31% → 57.63% |
| CROSSED | 차이 없음 | 21.67% → 21.67% |

- **이득은 단가보다 체결률에서 먼저 온다.** BALANCED에서 KRX만 쓰면 낸 수량의 절반만 체결된다
- 세 복수시장 전략의 평균 단가가 같은 것은 반올림이 아니라 **같은 호가를 다 먹기 때문**이다.
  차이는 채우는 순서, 즉 주문마다 잰 슬리피지(0~2bp)에서 난다
  ([`strategies-2026-09-16.md`](bench/results/strategies-2026-09-16.md))

**성능 — 한 프로세스 안 7단계, Release, 단일 스레드** ([`pipeline-2026-09-16.md`](bench/results/pipeline-2026-09-16.md))

| 항목 | 저널 끔 | 저널 켬 (레코드마다 fsync) |
|---|---:|---:|
| 전 구간 p50 | 351 ns | 2.66 ms |
| 전 구간 p99 | 1,452 ns | 4.46 ms |
| TPS | 1,534,801 | 376 |
| 가장 비싼 단계 | SOR 계획 (50.7%) | 저널 기록 (99.8%) |

매칭 엔진만 따로 재면 400만 TPS 안팎이다([`2026-09-15.md`](bench/results/2026-09-15.md)).
이 숫자들에는 프로세스 사이 전문 송수신 비용이 **빠져 있다.**

## 구조

```
프론트엔드 (React, web/)
      │ REST / WebSocket (개발 서버 프록시로 같은 출처)
채널계 (Java / Spring Boot, channel/)
      │ 고정 길이 전문 (TCP)
원장 데몬 ledgerd (C, ledger/)
      ├─ 계좌·증거금 검증
      ├─ SOR (sor/) ── 통합 호가창, 최선집행 평가, 전략
      └─ 매칭 엔진 2종 (exchange/) ── KRX형 / NXT형
```

**지금 띄우는 모습은 위와 같다.** SOR과 두 매칭 엔진이 원장 프로세스 안에 있다.
설계 그림(원장·SOR·FEP·거래소가 모두 별도 프로세스)으로 가는 조각 — FEP의 epoll 루프,
세션·시퀀스 복구, 미응답 판정 — 은 `fep/`에 있고 두 프로세스 통합 테스트(T3-15)로
검증했지만 데몬으로 묶어 띄우지는 않았다. 이유는 [`docs/PROGRESS.md`](docs/PROGRESS.md)의 T6-03.

그 밖에 `core/`(전문·저널·스냅샷·대사), `bench/`(측정 하네스), `sdk/`(전략 엔진용 주문 SDK).

## 두 가지 모드 (Phase 8)

호가창을 **무엇이 움직이는가**가 다를 뿐, 두 모드가 같은 원장·같은 전문·같은 매칭 엔진을 쓴다.
주문은 어느 모드에서도 이 프로젝트의 원장 안에서 끝난다 — **바깥으로 주문이 나가지 않는다.**

| | 시뮬 모드 (기본) | 실시세 모드 |
|---|---|---|
| 호가를 만드는 것 | 가상 참가자(시드 유동성 + `ledgerd --live` 틱) | 바깥에서 받은 실호가 스냅샷(`MSG_BOOK_FEED`) |
| 시장 | KRX · NXT 둘 | **하나**. 국내 실시세는 통합(KRX+NXT)이라 나눌 시장이 없다 |
| SOR 배분 | 전략 4종이 나눈다 | 할 일이 없다(나눌 시장이 없다) |
| 전략 비교·측정 | 여기서만 가능 | 불가 |
| 재현성 | 시드 고정 | 녹화 파일 재생이 같은 결과를 만든다 |
| 피드가 멈추면 | 해당 없음 | **호가창이 얼어붙는다.** 가상 참가자가 대신 끼어들지 않는다 — 그러면 "실시세인 척하는 시뮬"이 된다 |

**실호가를 받아도 매칭 엔진을 빼지 않는다.** 실호가 10단을 내 호가창에 심고, 체결은 여전히 내
엔진이 판정한다. 체결 판정기를 따로 만들면 십중팔구 "그 가격에 거래가 있었으니 체결"이라는
순진한 판정이 되어 체결률을 부풀린다. 내 엔진은 가격-시간 우선순위를 재현하므로 내 주문이
**기존 잔량 뒤에** 줄을 선다. 바꾸는 것은 엔진의 입력뿐이다.

**모의투자로서의 한계.** 내 주문이 실제 호가를 소모하지 않으므로 **시장 충격을 재현하지 않는다** —
바깥 시세는 내가 무엇을 하든 그대로 흘러간다. 큐 우선순위는 재현한다(내 앞의 잔량이 먼저 빠져야
내 차례가 온다). 그래서 **호가 한 단을 흔들지 못할 만큼 작은 주문**에서만 받아들일 만한 근사다.
호가 잔량의 몇 %를 넘는 주문이라면 시뮬 모드의 측정 결과를 봐야 한다.

실시세는 토스증권 Open API의 **읽기 경로만** 쓴다. 주문 API는 호출하지 않는다 — 모의투자
샌드박스가 없어 같은 키로 실주문이 나가기 때문이다. 키는 저장소 루트의 `.env`에서 읽고
그 파일은 `.gitignore`에 있다(예시는 [`.env.example`](.env.example)).

## 실행

C는 WSL(Ubuntu), Java·React는 Windows에서 빌드한다(`CLAUDE.md`에 이유).

```bash
# C — 빌드와 테스트 (WSL)
cmake -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build
ctest --test-dir build --output-on-failure

# 메모리 검사
cmake -B build-asan -DCMAKE_BUILD_TYPE=Debug -DENABLE_ASAN=ON
cmake --build build-asan && ctest --test-dir build-asan

# Java — 테스트 (channel/)
./mvnw.cmd test
```

**화면까지 띄우기** — 터미널 셋.

```bash
# 1. 원장 (WSL). 9100번에서 기다린다
./build/ledger/ledgerd
# --live <초당 주문 수>를 주면 가상 참가자가 계속 주문을 내 호가창이 스스로 움직인다
./build/ledger/ledgerd 9100 --live 40

# 2. 채널계 (Windows, channel/). 8080번
./mvnw.cmd spring-boot:run

# 3. 화면 (Windows, web/). http://localhost:5173
npm install
npm run dev
```

화면이 `/api`와 `/ws`를 개발 서버를 통해 채널계로 보낸다(`web/vite.config.ts`).
원장을 껐다 켜면 호가창과 계좌가 처음 상태(시드 고정)로 돌아간다.

**실시세 모드로 띄우기** — 화면 오른쪽 위에 지금 어느 모드인지 늘 보이고, "시세 모드와 가격"
칸에서 바꾼다.

```bash
# 가) 토스증권 실시세. cp .env.example .env 후 키를 채우고
TOSS_ENABLED=true ./mvnw.cmd spring-boot:run

# 나) 녹화한 장 재생 — 장 마감·주말에도 데모할 수 있다. 같은 파일은 같은 결과를 만든다
FEED_REPLAY_FILE=../docs/samples/feed-sample.jsonl FEED_REPLAY_SPEED=3 ./mvnw.cmd spring-boot:run

# 받는 스냅샷을 파일로 남기려면
FEED_RECORD_FILE=../tape.jsonl ./mvnw.cmd spring-boot:run
```

`docs/samples/feed-sample.jsonl`은 **합성 샘플**이다(키 없이 재생 경로를 볼 수 있게 만들었다).
실제 장을 보려면 `FEED_RECORD_FILE`로 녹화한 파일을 쓴다.

토스에 붙지 못하면(허용 IP 미등록이면 `403 IP address not allowed`) 그 이유가 화면에
그대로 뜨고, 재생 파일이 있으면 그쪽으로 넘어간다.

화면의 **차트는 토스의 1분봉·일봉(OHLCV)**이다. 바깥 시장의 체결을 집계한 것이라 이
프로젝트 원장의 호가창과는 **별개의 데이터**다 — 시뮬 모드의 가상 참가자가 만든 체결은
봉에 섞이지 않는다. 키가 없으면 내 호가창의 중간가 선으로 되돌아간다.

**종목의 실제 가격에 맞춰 원장을 띄워야 한다.** 호가창은 기준가 ±30%(가격 제한폭)만
펼쳐 두므로, 그 밖의 실호가는 통째로 버려진다(화면이 그 사실을 알려 준다).

```bash
./build/ledger/ledgerd 9100 --live 40 --ref-price 260000   # 005930이 26만원대일 때
```

바깥 시세를 받은 시장에는 `--live` 틱이 더 끼어들지 않는다 — 실호가 위에 가상 참가자의
주문을 계속 얹으면 그건 실시세도 시뮬도 아니다.

**측정 다시 돌리기** (WSL, Release)

```bash
cmake -B build-rel -DCMAKE_BUILD_TYPE=Release && cmake --build build-rel
./build-rel/bench/compare_strategies 2026-09-16   # 전략 비교 표
./build-rel/bench/quality_report 2026-09-16       # 시드 30개 리포트
./build-rel/bench/bench_pipeline 2026-09-16       # 7단계 성능
./build-rel/bench/bench_match                     # 매칭 엔진만
```

## 단순화한 부분

실제 시장과 다르게 구현한 지점. 완전한 재현이 목표가 아니라
백테스트의 낙관적 가정을 제거하는 것이 목표다.

| 항목 | 실제 | 이 프로젝트 |
|---|---|---|
| 단일가 매매 | 시가·종가 단일가 존재 | 미구현. 연속 체결만 |
| 호가 단위 | 시장·종목별 차이 | 단일 테이블로 통일 |
| 청산·결제 | KRX가 수행 | 범위 밖 |
| 증거금 | 종목·계좌별 복잡한 산정 | 증거금률 100%, 현금 잔고 기준 |
| 중간가 세부 규칙 | 공개 자료 불충분 | 자체 판단, 근거는 `docs/decisions/` |
| 시장 감시 | CB, 사이드카 등 | 미구현 |
| 시장 충격 (실시세 모드) | 내 주문이 호가를 소모하고 시세를 움직인다 | 재현하지 않는다. 바깥 시세는 내 주문과 무관하게 흘러간다. 큐 우선순위는 재현한다 |
| 화면 데모 | 계좌·종목 다수 | 계좌 하나, 종목 하나(005930). 취소는 되고 정정은 원장이 "미지원"으로 답한다. 체결 내역은 화면을 연 뒤의 것만 보인다 |

## 출처

이 프로젝트는 **공개 자료와 자체 설계만으로** 작성되었다.
거래소·증권사의 비공개 프로토콜 규격이나 내부 시스템 구조는 일절 반영하지 않았다.

전문 레이아웃, 세션 프로토콜, 매칭 세부 규칙은 모두 자체 설계이며
실제 시스템과 다르다.

참고한 공개 자료

- 자본시장과 금융투자업에 관한 법률 제68조 (최선집행의무)
- 넥스트레이드 공개 시장 운영 안내
- 한국거래소 공개 자료
